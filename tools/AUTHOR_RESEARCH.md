# 公开作者身份研究与证据留档

本指南供公开作者资料补充、旧账号追溯和跨 AI 交接复用。领域语义以[作者专题](../docs/domain/authors.md)为准，出站访问与个人数据保护以[安全专题](../docs/SECURITY.md#作者公开资料出站访问)为准，落库使用[受控填充工具](README.md#作者公开档案受控填充)。

## 工作边界与完成条件

先确认本轮范围包含研究、审核、实际填充中的哪些步骤。研究与交接阶段只读取公开资料，产物写入 Git 忽略的本地目录。实际填充需要用户当前授权，并沿用正式 API 与 revision 冲突保护。

一轮研究以每位作者都有结论、证据和未解决条件为完成条件。可靠来源不足时保留待核实结论，明确本轮已试方法及失败原因。后续有新线索时从留档继续。

内部作者 ID、原显示名、regular/COS 类型须原样保留。用于检索的 Unicode NFKC、简繁体、空格和大小写变体另记在 queries；花体字归一化只用于发现线索。相同公开身份对应多个内部 ID 时分别留档，合并实体另按用户授权处理。

## 查询顺序

1. 阅读最近一次主代理结论、纠错记录和待补证据。旧批次和原始页面保留日期，核对后续修正是否已经覆盖旧结论。
2. 优先使用用户提供的来源 URL、归档注册表或来源文本确定账号线索。只读取与本次作者有关的公开账号字段，记录用户确认的具体范围。
3. 打开创作者官网、链接聚合页或已知平台主页，提取昵称、自述、平台链接和稳定用户 ID。
4. 沿主页外链交叉检查 X、Patreon、FANBOX、Pixiv、SubscribeStar、Bluesky、Iwara、Fantia、微博、B站等平台。平台别名变化需要互链或稳定 ID 支持。
5. 对短名、通用词、已移除页面和无主页线索的作者做定向检索，第三方目录只用于发现待核实的地址与旧 ID。
6. 逐条区分主号、备用号、粉丝号和失效旧号，记录排除依据，再独立核对头像。

## 来源与具体方法

| 来源 | 读取内容与方法 | 判断边界 |
|---|---|---|
| 创作者官网、Linktree、Carrd、AllMyLinks | 自述、主副账号、跨平台外链 | 聚合页中的每条链接仍需核对归属与可用性 |
| X | 公开主页、昵称、简介、外链与数字用户 ID；历史探针也可读取 FxTwitter 公开响应 | handle 可改名或被他人占用，数字 ID 与查询日期一起保存；第三方接口失败只记录本次读取结果 |
| Patreon | 创作者主页、vanity、可取得的 user ID/campaign ID、社交外链 | user ID 与 campaign ID 分开标记；跳转目录、Removed 和审核中分别记录 |
| FANBOX / Pixiv | 主页或公开响应中的 userId、creatorId、iconUrl、profileLinks | slug、Pixiv 用户 ID 与展示名分别保存；头像取作者 icon |
| Iwara | 公开 profile 中的 user.id、username、body；必要时进一步阅读该作者作品简介 | 简介为空时，创作者自行发布的作品简介可能包含关键平台外链 |
| Bluesky | 公开 profile、handle、可取得的 DID、简介外链和作者头像 | handle 与 DID 分开保存，第三方页名相同不足以确认 |
| 微博 / B站 / Fantia | 主页、UID/数字账号、本人自述及站外互链 | 访客墙、年龄门、风控响应单列，不据此认定账号不存在 |
| 搜索引擎 | 原名、规范化变体、平台限定及已知 handle 的组合查询 | 摘要仅用于发现页面，优先打开原始来源确认 |
| 第三方作者目录、转载页或历史索引 | 历史 handle、平台数字 ID、旧链接与改名线索 | 标记第三方来源，回到创作者可控页面验证；内容相似或索引同名不直接升级确认 |

历史探针使用过 `https://api.fxtwitter.com/<handle>`、`https://api.iwara.tv/profile/<username>`、`https://api.iwara.tv/videos?user=<uuid>`、`https://api.iwara.tv/video/<id>` 与 FANBOX 的公开资料响应。它们属于研究时观察到的读取入口，服务可用性和响应结构应按查询日期重新核对。仅读取公开可访问内容，访问限制按实际失败留档。

Iwara 的复核顺序是 profile → user.id → 作品列表 → 必要的少量作品简介，记录具体提供外链的作品 URL。作品页由创作者控制这一条件应能说明，转载内容里的“Official Site”仍需独立核对。

### 作品反向识图与历史线索

用户授权向指定搜索服务提交作品截图后，可尝试 Google 图片或 Lens 反向识图。记录提交的截图摘要、搜索服务、时间、匹配页面与实际结果，选择足以辨识作品的必要画面。文字关键词搜图和上传截图反向识图分别记录；网页访问、文件上传或验证码受限时明确说明实际完成的步骤。

由识图发现的转载、作品名、水印或签名可继续用于检索。身份结论仍需回到创作者可控来源、稳定用户 ID 或可复核的公开历史资料。账号被封、改名或退隐时，组合旧昵称、作品标题、签名、水印、提及账号、推文关键词和公开转发关联查询，记录存档日期与原始 URL。

GitHub 公开仓库、Issue 或公开历史记录也可能提供旧账号与主页线索。搜索仅提交必要的公开名称或作品特征，源码引用和第三方清单按来源类型标记，再核查账号归属。外部识图授权范围、允许提交的素材与研究执行分工写入本地任务书。

## 判定与纠错

| 判定 | 所需依据 |
|---|---|
| confirmed | 创作者可控来源间的身份互链成立，名称差异可解释；用户明确确认的归属也可采用，但须单独记录确认内容与后续核对依据 |
| likely | 单一强来源符合名称与创作方向，仍缺独立的身份连接 |
| candidate | 同名、近似名或历史索引提供线索，尚不能排除其他人 |
| mismatch | 某候选账号有证据属于他人，或候选链接实际指向其他实体 |
| unresolved | 本轮没有取得足以关联身份的证据 |

同一作者可同时有待核实结论和多个 mismatch 候选。把错误账号写入 rejected_candidates，避免下一轮重复认领。合集名、占位分类应注明 entity_type 判断与依据。

明确分开记录 HTTP 状态、页面可见性和身份判定。403、404、登录页、解析失败和无搜索结果各自只能证明本次观察到的状态。即使头像和昵称相同，仍须核查主页互链、稳定 ID 与用户已确认线索。

历史结论修正采用追加记录，包含旧结论、新证据、变更原因和日期。批次结论与主代理最终结论有分歧时，两者均保留，说明采用哪一项及理由。研究 verdict 与产品 empty/candidate/verified 状态分开维护。

## 记录格式

每位作者至少保存以下内容，完整格式可在本地交接包中实例化。

- 原样身份字段 internal_id、original_name、kind。
- verdict、判定理由、缺失证据、需要复核的问题。
- platform、handle、稳定用户 ID 及其 ID 类型、URL、公开昵称和中性自述。
- queries、查询时间、读取工具/方法、来源 URL、HTTP 状态及访问限制。
- identity_links，写清来源 A 的哪个字段指向来源 B，避免仅列一组链接。
- rejected_candidates，包含排除过的 URL、原因和证据。
- avatar_source_url、来源属于本人头像的依据、格式/大小/摘要校验与产品代理读取结果。
- 历史批次及纠错引用、主代理审核状态、是否已实际应用。

原始公开响应与提取结论分别保存。每个快照记录查询时间、原始来源和 SHA-256；旧缓存保留原时间，重新查询使用新文件。查询结果中可能出现的联系方式、签名链接或无关个人资料仅留必要部分，交接前检查凭据和无关数据。

## 头像与网络排查

头像优先来自平台明确的 avatar/icon 字段。HTML 的 og:image 可能是宣传卡片或作品封面，应单独确认其用途。保存来源 URL，下载后检查 PNG/JPEG/GIF/WebP、实际读取大小及 SHA-256；预算沿用安全专题。

区分源图片下载成功、产品认证头像接口成功、客户端实际显示三种证据。遇到失败先检查来源响应、重定向、超时、图片类型和 DNS 地址。系统代理的 fake-IP 地址可能被产品出站校验拒绝，应保留安全校验，并在用户授权范围内调整特定域名解析。修改配置文件后须核对运行配置、DNS 结果与头像接口，脚本保存完成本身只能证明文件已保存。

网络状态改变后仅复查受影响项；偶发失败可在明确原因或先前成功证据下做一次有界复查，记录前后结果。持续失败保留现状和原因。

## 本地目录与交接

建议使用以下结构，所有真实作者资料均放在忽略的 audit 目录。

```text
audit/author-research.local/
  README.md                 当前研究资料入口与权威顺序
  methods/                  本轮使用的方法快照
  source-manifest.json      既有证据路径、摘要与用途
audit/authors-pending.local/
  README.md                 交接范围、状态与文件说明
  给其他AI的任务.md          可直接交接的研究要求
  pending-authors.json       待复核记录
  authors/                  逐人任务、历史证据与查询方向
  evidence-cache/           仅本批相关公开响应
  results/                  新结论输出位置
```

交接前检查待核实清单与已应用清单互斥、记录数相符、每人都有待补问题、源文件链接和摘要可核对。其他 AI 在自己的结果文件中写研究结论，主代理审核后生成新的受控填充输入。归档保留旧报告与原始缓存，最新入口明确标注结论修正和应用状态。

## 项目环境内的历史探针

若本地仍保存 `audit/verify/probe.local`，先阅读其源码、依赖与当前使用说明。它是历史研究脚本，查询会更新本地缓存，缓存过期策略和错误语义须按实际实现判断。以下命令按需单项运行，工作目录为项目根。

```powershell
python -X utf8 audit/verify/probe.local fx <handle>
python -X utf8 audit/verify/probe.local probe <公开HTTPS主页>
python -X utf8 audit/verify/probe.local iwara <username>
python -X utf8 audit/verify/probe.local iwaraworks <username>
python -X utf8 audit/verify/probe.local patreonuser <user-id>
python -X utf8 audit/verify/probe.local search "<名称>" --engine bsky
```

其余历史入口包括 `x`、`bili`、`booth`、`dlsite`、`sitesearch`、`kemono`。按任务选择，保存实际命令和结果；批量 collect/xfill 只在本轮明确需要重新研究整批时使用。未具备项目环境时可直接依据交接文件中的公开 URL 与待补证据逐项查询。

通用方法随代码管理。作者名单、研究报告、来源缓存、头像、个人归档映射与实际库统计保留本地，避免进入仓库、构建产物或公开交付记录。
