# ADR-0038：跨端文件移动不覆盖既有目标

## 背景（Context）

2026-10-15 可靠性加固批次并入时的决策固化（内容来源：`codex/reliability-hardening-ui-2026-10` 分支审查择优 + 防退化修订）。

问题：`filing.MoveFile` 原先直接 `os.Rename(src, dst)`——Unix `rename(2)` 与 Windows `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` 都会**静默替换已存在的目标**。回收站进/出、本机同步落位/移回、媒体归档等链路的目标冲突目前靠业务层（`ResolveConflict` 同名加序号、恢复自动改名）规避，但"业务层漏判"或"存在性检查与移动之间被并发创建目标"时，会无声覆盖用户文件——媒体库项目里这是数据损失的最后一环。Android 归档同理：`File.renameTo` 与 `Files.move`（不带 `REPLACE_EXISTING`）各有覆盖/检查语义差异，需统一口径。

备选方案：① 维持覆盖语义，全靠业务层检查（否——分散在多个调用点，静默丢文件的后果不可接受）；② 只改回收站链路（否——本机同步/归档链路有同族风险）；③ 在 `filing.MoveFile` 统一收口「拒绝既有目标」+ 哨兵错误（选）。

## 决策（Decision）

1. **服务端搬移语义收紧（`server/internal/filing/move.go`）**：`MoveFile` 在 `os.Rename` 前 `Lstat` 拒绝已存在目标（返回哨兵 `ErrMoveTargetExists`，绝不覆盖）；跨卷 copy 回落用 `O_CREATE|O_EXCL` 独占创建作第二道保护；非跨卷 rename 失败包装 `ErrMoveDidNotCreateTarget` 并保留底层错误（`errors.Is` 可判）。
2. **回收站清理口径**：`trash.go` 三个调用点的失败残留清理（`cleanupMoveResidue`）在命中上述两种哨兵时**跳过**——本次没创建目标就不能把它当半截副本删，防误删并发外部写入的完整文件。
3. **Android 归档同口径（`InboxFileStore.kt`）**：同卷优先**无覆盖改名**（`renameTo` 前置 `exists()` 检查）；跨卷走受控复制（唯一 `.part` 临时名 + 无覆盖发布 + 失败只清本次创建的临时文件）。
4. **两处实现红线（2026-10-15 审查教训）**：
   - **禁止用 `Files.getFileStore` 判卷**——AOSP 上 `UnixFileSystemProvider`/`LinuxFileSystemProvider` 的 `getFileStore` 是 Android-changed 的无条件 `SecurityException`（SELinux 策略），`runCatching` 吞掉后会让每次归档静默退化成本地整文件复制（大文件慢一倍 + 瞬时双倍空间 + 空间紧张时归档失败），且 JVM 单测不可见。改用「先试改名、失败再受控复制」的无探针路径，真机与 JVM 走同一代码。
   - **禁止直接 `Files.move` 交给标准库处理跨卷**——libcore `UnixCopyFile.move` 在 EXDEV 时自行 copy+删源，绕开本模块「唯一临时文件 + 无覆盖发布 + 失败即清理」的受控路径。
5. **刻意不做**：不宣称消除跨进程 TOCTOU（标准 API 无原子 no-replace 原语，检查与移动之间的窗口保留——边界与验收矩阵记档 SECURITY.md）；不引入跨进程锁/协调（单用户单机形态成本不值）；不改 DOMAIN_RULES §9「同名自动重命名永不 409」业务语义——业务层冲突处置（`ResolveConflict` 加序号、TXT 归档同名只留最新先 `os.Remove` 再搬，ADR-0030 修订1）不变，本决策只是把兜底不变量从"静默覆盖"改为"显式失败"。
6. **CI 覆盖**：新增 Windows 原生 runner 的 `go test ./internal/filing` job，覆盖 Linux job 不编译的 `move_windows.go` build-tag 路径（Windows 双盘是本机日常形态，2026-10-11 已有该路径漏判事故）。

## 状态（Status）

Accepted（2026-10-15）。

## 后果（Consequences）

- **积极**：「静默替换用户文件」在服务端搬移与手机端归档两条主链路上被堵死；冲突变为显式失败（哨兵可判、可重试、可告警），回收站清理不再有误删外部文件的口子；Android 归档同卷快路径在真机恢复为瞬时改名（2026-10-15 审查修复），并有 mtime 断言测试锁定。
- **代价与风险**：原先依赖 rename 覆盖语义的行为变化是**失败安全**——本机同步「落位后移回」在源被重新投放时改为保留库位件 + 告警、下轮重新观测（不再吞掉新投放文件）；回收站冲突场景报错而非替换（与"该副本可能是唯一完好副本"的设计意图一致）。真实双挂载点跨卷行为仍待部署环境端到端验收（SECURITY.md 矩阵）。
- **受影响文件/文档**：`server/internal/filing/move.go`、`move_test.go`、`server/internal/httpapi/trash.go`、`server/internal/httpapi/localsync_runner.go`（调用方语义）、`android/core/data/src/main/java/media/qimeng/app/core/data/repository/InboxFileStore.kt`、`InboxFileStoreTest.kt`、`.github/workflows/ci.yml`（server-windows-filing）、`docs/SECURITY.md`（「文件移动 / 回收站的跨卷安全边界」节）、`docs/adr/0030`（归档同名只留最新实现依赖本 ADR 的显式失败语义自愈）、`docs/adr/0024`（归档同名语义）。
