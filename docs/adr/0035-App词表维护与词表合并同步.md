# ADR-0035：App 词表维护（本机词表直接编辑）与词表合并同步

## 背景（Context）

ADR-0034 落地了「词表同步」：NAS/电脑端为唯一权威源，App 远程登录态下单向下发覆盖
本机内嵌库。上线当天用户试用后连续拍板三点定稿（同日语录：「没有手动维护功能啊，
只允许走 NAS 同步过来？？双向的手机也可以同步到 NAS，以及输入出处的维护手机也可以，
加上去」「添加框太复古了，统一设计元素」「直接走备份那边一起吧，这样明确一点。词表
和其他的不一样，只会多加不会删除，所以两边合并是增量不会出奇怪的问题」）：

1. **手机要能直接编辑本机词表**（ADR-0034 记档推迟的「App 端词表编辑 UI」转正）；
2. **同步语义改为两端增量合并**——词表与媒体库/统计不同，工作流只有补录没有删除，
   并集合并不丢任何一端的词条，覆盖式同步（单向或双向）及其确认防线整体不需要；
3. **同步入口迁入「备份导入导出」页**——数据流转类功能集中一页，比独立 hub 行更明确；
   添加词条的输入框统一 App 胶囊输入面（QimengCapsuleTextField），不再用 M3
   OutlinedTextField 描边框。

服务端/openapi/SDK 零改动继续成立：GET/PUT /sources/custom-groups 两端点已同时承载
读与写（ADR-0033），合并同步只是客户端编排。

## 决策（Decision）

1. **词表维护子页（本机词表直接编辑面）**：数据管理 hub 新增「词表维护」入口行 →
   编辑子页。**无门禁**（编辑对象恒为本机内嵌库，不涉远端；本机模式内嵌服务端本就
   在跑，远程登录态按需拉起、收尾停回）。交互为「内存编辑 + 整体保存」：进页 GET
   全量词表 → 组（规范名改名/移除、变体增删、角色增删/改名、别名增删）与停用词
   增删全部是纯内存列表操作（dirty 置位）→ 保存按钮整体 PUT（恒显式 groups+stopWords
   数组）——协议整体替换语义天然对齐「用户看到什么就保存什么」；保存成功后**静默
   回读**生效形态抹平服务端规范化差异（trim/去空/去重/canonical 自并入变体别名）。
   输入侧按协议容量投影封顶（VocabularyLimits：组 256/变体 64/角色 128/别名 32/
   停用词 256/单串 100，常量注释标注与 openapi.yaml 双同步责任）；有未保存修改时
   返回走放弃确认（系统返回与本页返回钮同口径）。输入面统一 QimengCapsuleTextField
   （全仓输入面统一语言），带字数回显。**弹窗容器显式落 surface（卡片面）**：M3
   AlertDialog 默认容器 = surfaceContainerHigh，与本主题夜间胶囊底 surfaceVariant 同档
   合并（旧版灰阶四档 1A/24/2E/38，Theme.kt），夜间弹窗里胶囊与弹窗底同色 #2E2E2E
   完全隐形（用户反馈「夜间胶囊不太行」根因）——落 surface 恢复「页面底 1A < 弹窗
   24 < 胶囊 2E」抬升梯度，浅色同构（弹窗纯白=卡片语言）。
2. **词表合并同步（定稿语义，取代 0034 覆盖式下发）**：备份页新增「词表合并同步」卡
   （与「同步浏览数据」并排；用户拍板「直接走备份那边一起」），**一键触发、无方向
   选择、无两段式确认防线**——合并无损即无需防线：
   - 链路：远端 GET（标准鉴权）+ 本机 GET（本机通道）→ [VocabularyMerger] 并集合并
     （纯函数，单测锁定）→ 合并结果显式 PUT 回两端 → 两端收敛到同一并集；
   - 合并规则（对齐引擎折叠口径与服务端 PUT 规范化）：折叠键 = trim + 忽略大小写；
     出处组按折叠键并集（远端在前、本机独有按原序追加；同键组并入——规范名保留先
     出现方写法、变体并集、角色按折叠键并集+别名并集）；变体/别名去重含「不与规范名
     自身重复」（GET 回读数据中 canonical 自并入变体的服务端规范化形态，合并滤除后
     PUT 由服务端重新补上，存储形态最终一致）；停用词并集；空表回 null；
   - 结果提示带增量数字：合并后组数/停用词数 + 远端补入 N 组 · 本机补入 M 组；
   - 失败分类沿用五支（NoAuthoritativeSource/RemoteFetchFailed/RemoteApplyFailed/
     LocalServerUnavailable/LocalApplyFailed）；任一端 PUT 失败时两端短暂不一致但
     零丢失，合并幂等、重跑即收敛（已知限制记档）。
   **被否决的方案记档**：①ADR-0034 单向覆盖（当日本已上线）与②双向手动覆盖（本批
   一度实施的方向化方案）——均被「词表只增不删，合并是增量不出怪问题」的用户拍板
   取代：覆盖语义的「独有词条丢失」防线在增删对称的数据上是必需品，在只增不删的
   词表上是多余负担；自动后台合并不做（同步仍是显式一键触发，不做后台轮询）。
3. **本机通道抽取共享**：0034 的「拉起内嵌服务端 → 端口就绪 → dev-login → 接线 →
   用完停回」编排出现第二个消费方，按代码卫生约束抽 `LocalVocabularyChannel`
   （core:data/embedded）单源收口——401 陷阱防线（@LocalDirectClient 零拦截器客户端、
   实例级 accessTokenProvider、与全局 NAS 会话互不接触）随抽取整体继承，两仓库
   （VocabularySyncRepository/VocabularyEditRepository）只补各自请求与错误归类。
   错误分类不另立平行枚举：词表维护复用 VocabularySyncError 的本地两支。
4. **UI 零业务规则（铁律 7）**：编辑操作全是 core:data 仓库端口后的 VM 内存列表
   操作；合并引擎是 core:data 纯函数；页面不持有任何地址/鉴权/协议知识。

## 状态（Status）

已接受（2026-10-04，用户当日三段拍板定稿）

## 后果（Consequences）

- 受影响文件（全部为 App 端，服务端/openapi/SDK 零改动）：`android/core/data/`
  （VocabularyMerger 纯函数新件、LocalVocabularyChannel 共享件、VocabularyEditRepository
  接口+Impl、VocabularySyncRepository 接口+Impl 合并化、DataModule @Binds）、
  `android/feature/manage/`（VocabularyEditViewModel/Screen/GroupsCard/Dialogs 新件、
  VocabularySyncCard 新件〔备份页卡〕、VocabularySyncViewModel 一键化、VocabularySyncScreen
  与词表同步 hub 行随入口迁移退役、DataManageScreen 改述）、`android/app/`（QimengNavHost
  词表同步路由退役、词表维护路由新增）、`docs/`（本 ADR、INDEX、GUIDE_API、HANDOVER、
  CHANGELOG）。`android/core/ui/`（QimengSegPill 增可选 enabled 参数——方向选择方案
  的遗产，向后兼容缺省保留）。
- 测试：VocabularyMergerTest（并集保序/同键并入/角色与别名并集/停用词折叠去重/
  canonical 自并入滤除/空表归一）、VocabularySyncViewModelTest（一键同步/忙态防重/
  五支错误映射/失败重试）、VocabularyEditViewModelTest（加载回填/五层编辑置脏/可省
  字段空表归一/越界静默/保存携带与静默回读/失败保持脏态）。
- **Web 移植（2026-10-04 同日补记，用户拍板「词表维护移植到文件管理中，功能和
  ui 布局和 app 的一致」）**：数据管理 hub 新增「词表维护」入口卡（紧随「来源
  词表」）+ 子页 `web/src/pages/VocabularyEditPage.tsx`（配套
  `components/manage/VocabularyGroupsCard`·`VocabularyEditDialogs`、
  `hooks/use-source-groups`、`lib/vocabulary-edit` 纯函数状态机——App
  VocabularyEditViewModel 编辑操作去 IO 化，14 例单测=VocabularyEditViewModelTest
  对位）。功能与 UI 布局对齐 App 端（组互斥展开/变体/角色/别名/停用词五层编辑、
  整体保存恒显式 groups+stopWords、放弃确认逐字文案、限额投影常量与 openapi 双
  同步）；两点端侧差异：①编辑对象=**当前连接服务器**（标准 Bearer 鉴权），非
  App 本机通道——web 无内嵌服务端概念；②「保存后静默回读」以 mutation 同步写
  缓存+失效重拉等价实现（规避重拉间隙闪旧值）。内置组数文案统一 133（2026-10-04
  固化后权威口径；App 端规则行的 130 系固化前陈旧文案，待 App 侧顺手勘误）。
  服务端/openapi/SDK 仍零改动。
- 已知限制：①合并引擎在客户端执行，超出协议容量上限（组 256 等）时由服务端 PUT
  校验兜底 400（实际词表体量距上限遥远）；②任一端 PUT 失败时两端短暂不一致，重跑
  即收敛（合并幂等）；③编辑页不去重（服务端 PUT 规范化去重，保存后回读抹平展示
  差异）；④同步/保存触发的后台全库重算在服务端自动进行，App 不等重算完成。
- 既有不变量维持：内置 133 组冻结基线不受词层操作影响（DOMAIN_RULES §4）；壳层
  「主键非本机预设=停服」（通道收尾守卫换端复查）；本地 token 与全局会话两套互不
  接触；dev-login 会话行随过期策略消亡；词表变更的存量传导复用 ADR-0033 闭环
  （PUT → 引擎同步替换 → 后台重算 → library.changed）。
