# ADR-0011：数据库演进式迁移纪律（只加不改不删）

## 背景（Context）

schema 演进唯一通道是 golang-migrate 迁移文件（ADR-0003）。但 AI 主力开发场景下最常见的数据库事故不是"跳过迁移"，而是"顺手改掉上一个迁移文件"：改 0002 里的列类型，本地库与新库从此分叉，用户 NAS 上已运行的库升级时炸掉且不可复现。迁移历史是**发布过的只读资产**，和 git 历史一样神圣。

## 决策（Decision）

1. **只加不改不删**：任何 schema 演进只**新增**编号顺延的 migration 文件（`server/migrations/`）；禁止修改已入库的历史迁移文件；禁止手改运行中的库（一切经迁移）。
2. **改/删既有结构走 expand-migrate-contract**：先 expand（新增新列/新表，代码双写/回填数据），观察稳定后再 contract（删除旧结构）——两步迁移，每步独立可回放。
3. **SQLite 删列的现实成本**：SQLite 删除列是重操作——旧版 SQLite（<3.35）根本不支持 `ALTER TABLE DROP COLUMN`，必须「建新表 → 拷数据 → 删旧表 → 改名 → 重建索引」整套重建；即使驱动带的新版支持，删列同样触发全表重写。因此**删列默认不做**，用「弃用不删」（列留库但代码不再读写）替代；确需删除时必须评估表规模并写进迁移注释说明取舍。
4. **新迁移只加文件**的语义同时约束 AI：写迁移前先 `ls server/migrations` 确认最大编号，新文件编号 = 最大值 + 1。

## 状态（Status）

Accepted（2026-08-26）

## 后果（Consequences）

- **积极**：迁移链从头可回放——新环境/CI/用户 NAS 升级走同一序列，schema 状态可复现。
- **积极**：expand-migrate-contract 让每次 schema 变更在任何时间点都可安全回滚，契合"用户 NAS 上有真实数据"的部署形态。
- **约束**：AI 发现历史迁移有错时，只能新增修正迁移（expand-migrate-contract），禁止回头改历史文件；迁移文件内必须写清"为什么"（对既有数据的影响）。
- **代价**：schema 会随演进积累少量弃用列/表——以空间换安全，符合 SQLite 单文件零运维的定位（ADR-0003）。
