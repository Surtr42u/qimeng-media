# ADR-0011：数据库演进式迁移纪律（只加不改不删）

## 背景（Context）

schema 演进唯一通道是 golang-migrate 迁移文件（ADR-0003）。但 AI 主力开发场景下最常见的数据库事故不是"跳过迁移"，而是"顺手改掉上一个迁移文件"：改 0002 里的列类型，本地库与新库从此分叉，用户 NAS 上已运行的库升级时炸掉且不可复现。迁移历史是**发布过的只读资产**，和 git 历史一样神圣。

## 决策（Decision）

1. **只加不改不删**：任何 schema 演进只**新增**编号顺延的 migration 文件（`server/migrations/`）；禁止修改已入库的历史迁移文件；禁止手改运行中的库（一切经迁移）。
2. **改/删既有结构走 expand-migrate-contract**：先 expand（新增新列/新表，代码双写/回填数据），观察稳定后再 contract（删除旧结构）——两步迁移，每步独立可回放。
3. **SQLite 删列的现实成本**：SQLite 删除列是重操作——旧版 SQLite（<3.35）根本不支持 `ALTER TABLE DROP COLUMN`，必须「建新表 → 拷数据 → 删旧表 → 改名 → 重建索引」整套重建；即使驱动带的新版支持，删列同样触发全表重写。因此**删列默认不做**，用「弃用不删」（列留库但代码不再读写）替代；确需删除时必须评估表规模并写进迁移注释说明取舍。
4. **新迁移只加文件**的语义同时约束 AI：写迁移前先 `ls server/migrations` 确认最大编号，新文件编号 = 最大值 + 1。

## 状态（Status）

Accepted（2026-08-26）

## 后果（Consequences）

- **积极**：迁移链从头可回放——新环境/CI/用户 NAS 升级走同一序列，schema 状态可复现。
- **积极**：expand-migrate-contract 让每次 schema 变更在任何时间点都可安全回滚，契合"用户 NAS 上有真实数据"的部署形态。
- **约束**：AI 发现历史迁移有错时，只能新增修正迁移（expand-migrate-contract），禁止回头改历史文件；迁移文件内必须写清"为什么"（对既有数据的影响）。
- **代价**：schema 会随演进积累少量弃用列/表——以空间换安全，符合 SQLite 单文件零运维的定位（ADR-0003）。

## 修订记录（2026-10-02，索引类迁移的计划影响横向复查）

**动机（0013→history 事故，真机复现）**：0013 为 stats 族引入 `view_events (kind, started_at)` 索引（审计 R4）时，验收只确认了目标查询族受益，未横向复查同表其余查询族的计划变化。本仓全库无 `ANALYZE`/`sqlite_stat1`，SQLite planner 纯启发式——**任何索引增删都会静默重排同表全部既有查询的执行计划**，坏计划不报错、只在规模放大后以性能事故显形。0013 实际后果：`ListHistory`（history.sql，当时的每资产 `MAX(started_at)` 相关标量子查询形态）被带进坏计划——该索引只能服务 `kind=?` 前缀（asset_id 不在索引列），每资产要扫全部 open 事件，真机 6350 资产 × ~6.8k open 事件 ≈ 4300 万索引步/请求，单页 8.85s 穿 App 10s 读超时 → 浏览历史页空白。0015 覆盖索引 `(asset_id, kind, started_at)` 应急止血（PR #4，查询零改动）；同日治本批将 `ListHistory` 改写为主流 CTE 预聚合 JOIN 形态（消除逐资产相关探测这一被截胡载体），并新增计划锁定测试 `server/internal/store/db/history_plan_test.go`（确定性断言 `EXPLAIN QUERY PLAN` 文本：ListHistory 两分支走 0015 覆盖索引单趟扫描、无 GROUP BY 临时树、无逐资产探测；facets 六查询共用的 history_subset EXISTS 走双等值前缀——后者即本轮横向复查发现的同型隐藏暴露面）。

追加决策（不改既有 1-4 条）：

5. **索引类迁移必须附「计划影响横向复查」**：对目标表在 `server/internal/store/queries/*.sql` 的**全部查询族**（不止目标查询族），迁移前后各跑一次 `EXPLAIN QUERY PLAN` 对照；对照结论（哪些查询族受益/不变/受损及取舍）写入迁移文件头注。有真机库只读副本时附规模化耗时对比。纯加索引 ≠ 零风险——验收对象是"同表全部查询族的计划"，不是"目标查询族的计划"。
6. **关键查询族计划入 CI 锁**：用户可见列表/统计主路径等性能关键查询族，其计划形态以确定性文本断言锁进测试（只比计划文本，不做耗时断言）；后续任何翻坏该计划的迁移会被 CI 拦截，迁移作者按第 5 条复查后随迁移同 commit 更新锁与断言。
