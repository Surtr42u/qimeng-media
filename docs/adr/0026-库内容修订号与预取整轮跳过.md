# ADR-0026：库内容修订号（library revision）与预取整轮跳过

## 背景（Context）

客户端缩略图预取（ADR 无独立文，见 `ThumbnailPrefetcher` 与 CHANGELOG 第四百一十一笔）每轮冷启动/重登录都要**全量分页拉取资产列表**（`GET /assets`，200/页）后做本地磁盘探测补缺。第四百一十一笔的磁盘探测短路已把"已缓存条目"的成本降到毫秒级，但列表拉取本身随库规模线性增长：10 万资产 = 500 页请求、几十 MB JSON，每次打开 App 都要拉一遍——这是大库下预取链路唯一剩的大头，且 `ALL_THUMBS_MAX_PAGES=200×200=4 万`的硬上限会在规模扩大后静默截断。

用户拍板"未雨绸缪、不计成本"扩规模（2026-09-30）。备选方案对比：

- **全套增量清单**（since 游标 + 变更日志 + 删除墓碑，Dropbox/Immich 模式）：把"变更轮"里已缓存条目的成本也省掉——但磁盘探测短路已把该成本压到毫秒级，增量清单买到的是边际收益，付出的却是状态机级复杂度（墓碑、游标过期回退全量、多端各自游标管理）。不选。
- **仅客户端优化**（第四百一十一笔现状）：列表拉取省不掉。不满足扩规模预期。
- **库 revision 比对跳过**（本 ADR）：库没变时整轮零列表请求，变了才全量拉列表+探测补缺。协议面一个字段、服务端一个计数器。**选它，且刻意不选增量清单**（见决策第 6 条）。

## 决策（Decision）

1. **全局单计数器 revision**（不分库，当前唯一消费方是全库预取）：持久化于 `kv_settings` 表键 `library_revision`（复用 migration 0003 的既有表，无新 migration）；自增为 SQL 侧单条 `UPDATE CAST(value)+1`（无读改写竞态），应用层互斥锁串行；键缺失时以 `COUNT(assets)+1` 原子播种基线（非零，避免与"客户端无记录"语义混淆）。值被外部改坏时端点 500 暴露而非静默重建伪值（`server/internal/libraryrevision/`）。
2. **bump 收口单点**：发 `library.changed` 事件的写路径（扫描全链/上传/回收站移入与恢复/整理移动/标签/库删除/库开关/手动扫描终态）统一在事件订阅处 bump 一处（`server.go` 订阅协程），不在 handler 重复加（防双重自增）；**不发事件的 4 条路径显式 bump**——回收站物理删除单条、清空回收站、到期清扫（removed>0）、qimeng-backup 导入成功（`bumpLibraryRevision` 全仓唯一出口，失败只告警：丢一次自增的后果是客户端至多多拉一轮，方向安全）。
3. **协议**：`GET /api/v1/library/revision` → `{"revision": int64}`（operationId `getLibraryRevision`，全局 bearerAuth 保护，无匿名豁免）。**语义边界**：只保证"资产集合/缩略图 URL 面"变更必然 bump；收藏、进度、作者展示字段等列表附属字段可无 bump 变化（当前唯一消费方只用 thumbUrl，无实害；未来若有整表缓存消费方须先扩 bump 面）。
4. **客户端跳过门**（`PrefetchRevisionGate` 纯函数 + `ThumbnailPrefetcher` 接线）：预取轮在就绪探针与计费网络门之后拉一次 revision，与 DataStore `last_prefetch_revision`（`PrefetchRevisionStore`）比对：serverRev=null→FULL（端点失败/旧服务端 404 降级）、lastDone=null→FULL（首次）、相等→**SKIP**（新终态 `PrefetchUiState.Skipped`，不调 allThumbUrls，UI 显示"缓存已是最新，本轮无需同步"）、不等→FULL。FULL 轮完成置 Done 前把轮首 revision 写回（null 不写保旧值；空库轮也写——下轮才能 SKIP）。所有失败降级方向均为"多做无害"（多拉一轮全量）。
5. **清缓存失效**：清空任一缓存池（NAS/本地）必须同时失效本地 revision 记录（`PrefetchRevisionStore.clear()`，由 `ThumbnailCacheViewModel.clearPool` 调用）——否则清空后库静态即永久 SKIP，预取失效且文案失实（reviewer P1）。清空后不即时触发新轮（与改动前一致：重登录/重启后补）。
6. **刻意不做（本 ADR 的"不做什么"）**：a) since 增量清单/墓碑/游标——规模到十万级或出现多端同步需求时再立项（届时从本 ADR 的 revision 语义起步扩，不推翻）；b) SSE 推送触发预取——国产 ROM 进程存活不可靠（凌晨轮中断实证），登录触发 + revision 跳过已够；c) 分库 revision——无消费方；d) `ALL_THUMBS_MAX_PAGES` 4 万硬上限与缓存档位 5GB 上限的调整属配置面，随规模实测另行处理（记入 HANDOVER 待办）。

## 状态（Status）

Accepted（2026-09-30）

## 后果（Consequences）

- **积极**：库未变的冷启动轮从"全量分页列表 + N 次探测"降到"1 次轻端点请求"；扩规模路径就绪（列表成本只在库真实变化时支付）；失败降级全部落在"多拉一轮"的弱失败方向。
- **代价与风险**：事件总线缓冲满丢弃时丢的自增造成"变更未 bump"窗口，漏同步持续到下一次任意变更（概率低，浏览时 Coil 懒加载兜底，同窗口早已影响推荐缓存失效——既有接受风险）；一次扫描可能发布两次事件（变更守卫 + FinishScan）使 revision 跳 2，方向安全（至多多拉一轮），系既有双发布非本批引入。
- **联动文件**：`api/openapi.yaml`（/api/v1/library/revision + LibraryRevision schema）、`api/sdk.lock`、`server/internal/libraryrevision/`（service+sqlc 查询+test）、`server/internal/httpapi/`（revision.go、server.go、trash.go、trash_sweeper.go、import.go、revision_test.go）、`server/internal/store/queries/revision.sql`、`server/internal/store/db/revision.sql.go`（生成）、`android/core/data/src/main/java/media/qimeng/app/core/data/prefetch/`（PrefetchRevisionGate/PrefetchRevisionStore/ThumbnailPrefetcher）、`android/core/data/src/main/java/media/qimeng/app/core/data/repository/`（LibraryRevisionRepository/SdkLibraryRevisionRepository）、`android/core/data/.../di/DataModule.kt`、`android/feature/manage/`（ThumbnailCacheViewModel/ThumbnailCacheScreen）、`docs/GUIDE_API.md`（路径 66→67）、`docs/CHANGELOG.md`（第四百一十二笔）、`docs/HANDOVER.md`、`docs/adr/INDEX.md`。

## 修订（2026-09-30 撞号与缓存漂移双修）

第四百一十二笔落地后复查确认两个真实缺陷，当日双修；修法全部失败方向落在「多拉一轮无害」，协议与服务端零改动。

- **缺陷 1（换端撞号）**：原记录只有 Long 修订号、不记是哪台服务器。本地端与 NAS 是独立修订号计数器、播种基线同为 `COUNT(assets)+1`，两端库规模相近时修订号完全可能相等——切服务器后被错误 SKIP，新服务器一张图没缓存过也永远不预取。原决策 4 论证「换服务端不区分是有意取舍：多跑一轮全量只耗带宽无正确性风险」是错的：真实风险恰恰是错误 SKIP（少拉）而非多拉。
- **缺陷 2（缓存漂移）**：Coil 磁盘缓存池 maxSize LRU 驱逐、系统存储紧张清掉整个 cache 目录——都不动客户端记录（在 filesDir 的 DataStore），「记录说全量、实际缺一片」且修订号不变则永不自愈。

7. **记录捆绑服务器标识**：`PrefetchRevisionStore` 记录升级为三元组（`last_prefetch_revision` 修订号 + 新增 `last_prefetch_server` 服务器标识 + 新增 `last_prefetch_sample` 随机抽样），`PrefetchRevisionRecord.serverKey` = 记录时连接的服务器 base URL **原串**，精确字符串比较、不做规范化——同实例换地址（IP↔域名↔回环预设）会多拉一轮全量，属「多拉无害」方向，不为地址等价规则引入复杂度。判定门 `PrefetchRevisionGate` 新增分支：`record.serverKey != serverKey → FULL`（换服务器必走全量，撞号修订号也不得 SKIP）；三键在同一次 DataStore edit 原子写入；存量只有旧版修订号键（无服务器键）的记录按无记录迁移（`lastDone()` 读回 null → 下轮 FULL 一次后写入完整三元组）。
8. **SKIP 前抽样核对**：全量轮完成时从全库缩略图 URL 随机抽 50 条（`PrefetchSampleGate.SAMPLE_SIZE`，用户拍板值）与修订号**同事务**落盘；SKIP 判定通过后逐条本地磁盘探测（`PrefetchDiskProbe` 按稳定键直查，URL 带过期签名不影响——探测前经 `SignedMediaCacheKeys.stableKey` 剥 exp/sig），缺失比例 ≥20%（`MISSING_THRESHOLD_PCT`，整数运算）即降级全量补拉并在轮末写回新样本（自愈闭环）。空样本（空库轮/旧记录/样本读失败）维持 SKIP——空库无片可缺；样本读失败而 revision 读取成功说明 DataStore 基本健康，且「读不到证据就多拉」会把单键损坏放大成每轮全量，与磁盘探测短路的优化定位不符。兜住缺陷 2 + 下方记档项三类「记录与实际脱节」。

记档项（不另修）：备份恢复会连 kv_settings 的 `library_revision` 一起回滚，理论上可与客户端记录撞号，由决策 8 抽样核对兜住。
