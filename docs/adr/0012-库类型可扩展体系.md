# ADR-0012：库类型（kind）可扩展体系——识别器分派 + 配套展示

- 状态：已接受（2026-09-03）

## 背景

用户对「库」的定义：**一种内容组织方式（文件夹结构）+ 与之配套的识别方式 + 对应的展示方式**，而非单纯的一个媒体路径。不同库的内容需要不同的解析和不同的浏览体验。

现有两种库类型（`libraries.kind`，扫描器按类型分派识别逻辑，DOMAIN_RULES §6）：

| kind | 识别方式 | 展示方式 |
|---|---|---|
| `normal` 常规库 | 靠**文件名**：扫描时跑 SourceMatcher（130 组出处检索表）提取出处/角色；作者靠 TXT 导入名匹配文件名（authoring） | 按日期/出处/角色/类型筛选，进常规浏览流 |
| `cos` COS 作者库 | 靠**目录结构**：`作者名/作品名/文件` 三层，按目录直接建 `cos_` 前缀作者，不解析文件名 | 作者/作品维度展示；COS 文件不进常规浏览流（browse `include_cos` 谓词） |

用户以后加新库可能采用**全新的文件夹方式**，需要为其定制识别规则才能正确展示内容——因此把"库类型可扩展"固化为架构决策，方便以后任何 AI 按此接手。

## 决策

1. **`libraries.kind` 是第一等扩展点**：新增一种库 = 注册一个新 kind 的识别器（识别器=「如何从目录/文件名提取作者/出处/角色等元数据」），不修改既有 kind 的行为。
2. **分派点唯一**：scanner 按 `kind` 分派入库富化逻辑（现有分派实现：normal → SourceMatcher + 作者名匹配；cos → 目录结构建 cos_ 作者，含孤立作者对账清理）。新 kind 在同一分派点挂新分支。
3. **新 kind 接入清单**（做时逐项打勾，全部完成才算落地）：
   - [ ] 目录/命名契约定义（写进 DOMAIN_RULES 新章节，逐字固化的口径）
   - [ ] 识别器实现为**纯函数**（无 IO，行为由单元测试锁定，照 SourceMatcher 模式）
   - [ ] 协议 `kind` 枚举扩展 → `make sdk` 三端重生成（铁律 1）
   - [ ] 前端展示适配：列表卡片/筛选维度/详情展示，必要时该 kind 独立浏览视图
   - [ ] migration 影响评估（是否需要新列/回填，只加不改 ADR-0011）
   - [x] 能力声明：是否支持作者挂靠——`Library.capabilities.authorAttach`（服务端 `scanner.SupportsAuthorAttach` 单一来源，2026-09-25 首例 normal=true/cos=false，ADR-0023）

   清单首例执行说明（2026-09-25）：第 6 项「能力声明」随 ADR-0023 上传挂靠批落地——kind 的能力差异从此进协议面（`Library.capabilities.*`），客户端按声明渲染功能入口（如挂靠输入段）、禁写死 kind 判定。
4. **与库开关（enabled）正交**：enabled 管"是否展示"（migration 0007：停用仅隐藏浏览面，记录全保留），kind 管"如何识别与展示"。两者组合覆盖"临时下线某类内容"与"接入全新内容体系"两个场景。

## 后果

- 加新库类型的成本 = 一个识别器（纯函数+测试）+ 展示适配 + 协议枚举扩展，不需要改全局架构。
- 识别逻辑保持纯函数边界（ADR-0010 模块边界），行为由测试锁定，展示层（铁律 7）不掺识别规则。
- 用户新增"全新文件夹方式"的库时，只需向 AI 描述目录契约，AI 按「新 kind 接入清单」执行。
