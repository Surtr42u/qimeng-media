# ADR-0010：模块边界三层强制（编译器 + depguard + lint 门禁）

## 背景（Context）

服务端是模块化单体（ADR-0002），模块边界 = `server/internal/` 包边界，依赖方向 `httpapi → 业务模块 → store`（ARCHITECTURE §5）。在 AI 主力开发的场景下，边界最容易腐化：业务包顺手 import 一下 httpapi 的类型、新模块直接引用 gen 包，几天内就长成意大利面。文档约束约束不了代码，必须让**机器**执行。

## 决策（Decision）

边界强制分三层，全部已在 2026-08-26 底层重构中落地：

1. **Go `internal/` 编译器边界**：所有业务包位于 `server/internal/`，Go 编译器保证模块外无法 import——零配置的物理隔离。
2. **depguard 两条红线**（`server/.golangci.yml`，golangci-lint v2.13.1）：
   - `httpapi/gen`（协议生成接口层）只允许 `httpapi` 包引用；
   - 业务包与 sysmon **禁止反向依赖 `httpapi`**；唯一例外 `cmd/qimeng`（main 组合根，依赖注入只在 main 发生）。用 `$all` + 否定式排除覆盖现有与未来全部新包，无需逐包登记。
3. **golangci-lint 门禁进 CI**：server job 在 vet/test/build 前跑 golangci-lint（golangci-lint-action@v9，版本与本机 Makefile 锁定一致）；本机 `make lint` 同配置，违规即红。

**明确不引 arch-go 等包级架构测试工具**：小众工具 AI 语料少、误报排查成本高、维护收益在当前 12 包规模下不成比例。约定优于配置——三层强制已经覆盖主要腐化路径；未来包数显著增长、需要表达"XX 包禁止依赖 YY"级精细规则时，再评估引入并以新 ADR 记录。

## 状态（Status）

Accepted（2026-08-26，已落地：.golangci.yml + ci.yml + Makefile lint）

## 后果（Consequences）

- **积极**：边界违规在本机 `make lint` 与 CI 双点即失败，依赖方向成为可执行事实。
- **积极**：未来新增业务包自动纳入 depguard 覆盖（否定式排除），零维护成本。
- **约束**：AI 新增代码若被 depguard 拦截，唯一合法出路是按依赖方向重构（HTTP 层类型下沉或经领域类型包中转），禁止给 depguard 开豁免口子（现有排除仅限 gosec 误报类，见 .golangci.yml 注释）。
- **代价**：cmd 组合根是唯一豁免区，main 里的装配代码规模会随功能增长——这是有意承担的成本，换来业务层纯净。
