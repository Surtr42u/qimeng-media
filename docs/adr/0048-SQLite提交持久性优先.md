# ADR-0048：SQLite 提交持久性优先

- 状态：已接受（2026-10-21；用户授权 AI 实施架构维护并继续完成清单）
- 范围：替代 store.Open 的 WAL/NORMAL 性能取舍；SQLite/sqlc/迁移体系与领域规则不变。

## 决策与依据

所有经 store.Open 打开的业务库默认 WAL + synchronous=FULL，逐连接由 DSN 下发，含连接池新建和重连。SQLite 官方说明：WAL/NORMAL 在断电或系统崩溃后可能回滚已提交事务，FULL 每次提交额外同步 WAL（[官方 PRAGMA 说明](https://www.sqlite.org/pragma.html#pragma_synchronous)）。本库不仅存可重扫资产，也存收藏、原始行为事件及手工编辑；这些数据不能靠扫描原件恢复。保留原有 immediate 写事务、分页和扫描/导入批次事务，不引入第二份业务真相或自研持久日志。

不新增面向普通用户的降级开关，也不在测试中放松生产默认值。如果真实设备提交延迟成为瓶颈，先定位事务边界与批量提交，不静默退回 NORMAL；确需调整时复查持久性承诺及实际写入负载。

## 验证与代价

2026-10-21 Windows 本机临时合成库、单连接、逐事务更新一条 kv、三轮 250ms 基准：NORMAL 中位数约 0.0203ms/事务，FULL 约 0.408ms/事务（约 20 倍，绝对增加约 0.388ms）。命令：`go test ./internal/store -run '^$' -bench '^BenchmarkCommitDurability$' -benchtime=250ms -count=3`。不把该数字外推为手机、NAS 或端点延迟。

回归检查迁移后同时持有的两条连接及池重连均使用 FULL(2)，原有升级/快照恢复/事件身份与业务测试继续执行。自动化只能核实配置和行为，不能通过测试模拟出硬件的全部掉电语义。

## 保留边界

- FULL 依赖 OS/文件系统/设备兑现同步，不保证坏盘、固件故障或数据目录与媒体文件的跨系统原子性。
- 备份仍需独立原件/密钥副本；FULL 不替代恢复演练。
- 本轮不操作 8420 真库、不部署手机，不做 NAS/真实掉电测试；运行中的旧包仍维持其原设置。
