# ADR-0004：数据身份机制（asset_id + 移动合并）

- 状态：已接受（2026-08-22）
- 本项目最重要的数据设计，AI 涉及数据层必读。

## 决策

- 主键 = **asset_id**（UUIDv7，终身不变）
- **路径是属性**：`library_id + 规范化相对路径`（唯一索引），不是身份
- 变更检测 = size + mtime；不一致 → 重探元数据
- 内容哈希**懒计算**（后台低优先级），用于去重提示，不阻塞扫描

## 背景：两条历史教训

1. 旧项目用「完整文件名」做主键 → 改名/移动/多目录同名即断链，靠 `@文件夹名`、`#路径哈希` 层层打补丁
2. 本项目早期讨论曾定「路径做身份」→ 但用户新增需求"App 内移动/重命名文件"后，路径身份同样断链

## 移动合并（两个来源）

| 场景 | 机制 |
|---|---|
| App/API 主动移动 | 服务端已知身份 → 直接更新路径属性，标签/作者/统计/收藏全保留 |
| 用户绕过系统在 NAS 文件管理器移动 | 扫描器启发式：旧路径消失 + 新路径出现 + size/mtime 一致 + 时间窗口内 → 自动判定移动并合并 |

启发式误判兜底：合并操作记录审计日志（可追溯）；启发式可通过配置关闭（极端谨慎用户）。

## 后果

- `recordKey` 概念彻底废弃；旧数据迁移时按文件名建立 recordKey→asset_id 映射（DOMAIN_RULES §10）
- 一切关联表外键指向 asset_id，永不引用路径
