# ADR-0029：SSE 数据新鲜度收敛——服务端补 favorite.changed / like.changed 轻事件（跨端收藏/点赞零感知根治第一半）

## 背景（Context）

轨迹审计（2026-10-01）确认：跨端改收藏/点赞后**其它端零感知**——服务端对 favorite/like 本来就不发任何事件（事件面只有 library.changed 等四类，语义边界=资产集合面），而 Android 不消费 SSE、Web 端虽消费 SSE 但事件清单里根本没有这两类信号。各端被迫各自绕弯：

- **Android**：进程内指纹门、ON_RESUME 跳过门、预取 revision 门（ADR-0026）等多套自制新鲜度门各自为政，第四百一十五笔又给收藏/点赞返回刷新叠加 5 分钟 TTL——本质都是"服务端不发信号，客户端只能猜"的绕弯子方案，陈旧窗口 = TTL 上限（5 分钟）。
- **Web**：靠窗口聚焦重取 + SSE 重连补偿（第四百一十六笔），但重连失效映射只覆盖 library.changed，收藏/点赞仍无实时信号。

根因单一：**服务端事件面缺两类信号**。客户端门再多也只是缩小陈旧窗口，消除窗口必须由服务端补发。

## 决策（Decision）

1. **服务端补两类轻事件**（`server/internal/events/`，本 ADR 第一半，已随本批落地）：
   - `favorite.changed` / `like.changed`，载荷同构为 `{"assetId": string}`（`events.EngagementChangedEvent`，两 topic 共用一型）。**轻载荷取舍记档**：写路径全是单资产操作（PUT /assets/{id}/favorite、PUT /assets/{id}/like，无批量接口；qimeng-backup 导入是历史数据回放不属于用户实时操作，不发），单 id 即全部信息；不带变更后状态（favorite 布尔/likeCount 数字）——事件是"变更信号"不是状态面，消费方重拉权威状态即可，避免载荷与 handler 状态计算形成第二份真相。
   - **发布点**：`server/internal/httpapi/engagement.go` 两个 handler 写成功后（发布在写响应之前）；404 路径零发布（行为测试锁定；like 的 count 回读失败 500 时事件已发但变更本身为真，无实害）。重复收藏的幂等 no-op（ON CONFLICT 0 行）照发——多刷一次幂等无害，发布点与写成功点一一对应更可审计。发布失败只告警不改变请求成功语义。
   - **不 bump 修订号（硬约束）**：favorite/like 不改变资产集合，ADR-0026 语义边界（revision 只保证资产集合面）不变。实现上零新增机制即成立——修订号自增订阅只挂在 library.changed 上，新事件天然绕开；此约束同时写进 events 包 topic 常量注释、载荷 KDoc 与 handler 注释，**防止未来有人拿 favorite 事件去 bump revision**。测试 `TestEngagementChangeEventsPublished` 行为级钉死（事件不混发 library.changed + /library/revision 前后相等）。
   - **SSE 通道零改动**：`allTopics` 增两枚举即接入既有流；Web SseBridge 按事件名分发，不认识的名字被忽略，对未接线的客户端零害。**运行时事件面不入 openapi.yaml**（SSE 载荷不进协议建模，事件清单以 GUIDE_API.md「实时推送」行为准；bus.go 既有"主题与 openapi 对齐"注释随之修订并记档此例外）。
2. **Android 接入 okhttp-sse 消费 + 门收敛到统一信号**（第二半，客户端批次落地，此处记录目标形态）：新增一条 SSE 订阅消费 favorite.changed/like.changed（连同既有 library.changed），作为收藏/点赞/列表数据失效的**统一新鲜度信号**；既有进程内指纹门、ON_RESUME 跳过门收敛为同一事件驱动失效，revision 预取门（ADR-0026）职责不变（它管资产集合面，与本事件面正交互补）。
3. **Web SseBridge 补失效映射**（第二半）：`web/src/lib/sse.ts` + `use-sse-events.ts` 为两个新事件名补查询失效映射（收藏页/详情点赞态/资产列表的 liked/favorite 字段面）。
4. **TTL 保留为离线兜底**：第四百一十五笔的 5 分钟 TTL 门不拆除——SSE 是尽力而为通道（总线缓冲满丢弃、断线窗口丢事件），离线/断连时 TTL 是唯一的自愈底线。事件驱动为主、TTL 兜底为辅，两层不互斥。

## 状态（Status）

Accepted（2026-10-01）

## 后果（Consequences）

- **积极**：跨端改收藏/点赞从"至多 5 分钟陈旧"收敛到秒级感知；Android 多套自制门有了统一信号源可收敛，猜测式新鲜度修补就此止步；事件面与修订号语义边界（ADR-0026）经测试锁定不漂移。
- **代价与风险**：SSE 尽力而为语义下事件可丢（总线缓冲满丢弃=既有接受风险适用、断线窗口错过即无补发）——**事件丢失窗口=回到 TTL 兜底**，失败方向弱（多陈旧一会儿，永不假新鲜）；未接线的旧客户端收到未知事件名按 SSE 规范忽略，零破坏。
- **联动文件**：`server/internal/events/`（bus.go 主题常量与例外记档、events.go 载荷、sse.go allTopics、sse_test.go 透传用例）、`server/internal/httpapi/engagement.go`（两发布点）、`server/internal/httpapi/engagement_events_test.go`（新）、`docs/GUIDE_API.md`、`docs/HANDOVER.md`、`docs/CHANGELOG.md`（第四百二十笔）、`docs/adr/INDEX.md`。`api/openapi.yaml` 与三端生成物零改动（运行时事件面，见决策 1）。第二半 Android 侧（okhttp-sse 消费 + 门收敛）**已随同日客户端批次落地**：ServerEventConsumer 登录即连/断线指数退避重连（3s 起 30s 封顶、登出即断、后台不断开，鉴权经派生客户端共享 AuthInterceptor）、DataFreshnessSignal 三计数信号汇（onOpen 重连 bump 对齐 Web 语义）、收藏/点赞跳过门收敛关联 favorite+library / like+library 两计数、TTL 降级为离线兜底（以本文"事件最终形态"为实现依据，测试全绿 + assembleDebug 通过）；Web SseBridge 失效映射（favorite→收藏面根键、like→资产/排行/推荐三根，onOpen 重连补偿同覆盖）亦已同日落地，本 ADR 端到端闭环。
