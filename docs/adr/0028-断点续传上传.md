# ADR-0028：断点续传上传（tus 1.0 核心语义极简子集——弱网大文件续传地基）

## 背景（Context）

现状上传 = 整文件单次 `POST /assets/upload`（octet-stream 流式直传）：弱网传大文件（NAS 场景主力：手机直传 2GB 视频）中断即从零重传；Web 端失败不重试，Android 端 WorkManager 重试也是整文件重来。移动网络下 2GB 文件传到 90% 断线，重试成本约等于零收益。主流方案 = tus/分片续传。

约束：
- 服务端已有久经考验的上传管线（filing 四道校验、库锁内冲突解析、persistUploadedAsset 单写事务、富化、library.changed / upload.done 事件、修订号 bump 经事件订阅收口）——续传通道必须复用而不是旁路它，否则出现"两条入库路径、两套校验口径"的分叉。
- 上传是个人 NAS 单用户场景：不需要多用户配额、不需要跨节点存储、不需要 tus 完整扩展面（Creation-With-Upload/Expiration/Checksum 扩展都不引入）。

## 决策（Decision）

落 tus 1.0 核心语义的极简子集，5 个操作 3 个路径模板，全部走全局 bearerAuth（无匿名豁免）：

1. **会话由服务端持有，客户端无状态**：`POST /api/v1/uploads` 创建会话（请求体 libraryId/fileName/size 必填、contentType/dir 可选），响应 `UploadSession{id, offset, size}`。创建即做可前置校验：文件名清洗（与直传同规则）、dir 目标目录校验规范化（与直传同一入口，决策 7）、扩展名白名单、size ≤ 上限、库存在且启用、upload.autoAccept 开关（与直传同一道闸，防分片通道成为直传被关后的旁路）——弱网传 2GB 前就把可预判的失败挡住。
2. **断点以服务端记录为准**：`GET /api/v1/uploads/{id}` 探测权威 offset（未知/已过期 404）；`PATCH /api/v1/uploads/{id}?offset=` 追加原始字节，offset 不等权威值 → 409 响应体即权威 UploadSession（客户端重同步后重发）；累计超 size → 400；单片超 32MB → 413（选型记档：分片超限是"载荷过大"用 413，声明不符的累计超限用 400）。磁盘写满/IO 错误 → 500 且会话保留可重试。
3. **complete 复用既有管线**：`POST /api/v1/uploads/{id}/complete` 对拼装完成的整文件复跑直传同一套终检（filing.ValidateUpload 四道校验：扩展名/魔数嗅探/最终大小/文件名 + 目标路径穿越检查），同名冲突语义与直传**逐字一致**——`filing.ResolveConflict` 自动重命名 "基名 (2).ext"、永不 409（DOMAIN_RULES §9 既有口径，本 ADR 不新造冲突语义；基线任务书提到的"conflictMode 同名二选一"经核实全仓不存在，现有上传通道历来自动重命名，执行时经确认按现状落）。成功走 `ingestPlacedUpload`（从直传 handler 抽出的共享入库管线）：library.changed 照发（修订号经订阅照 bump）、upload.done 照发、富化照跑，201 返回与直传同构的 AssetDetail。
4. **临时文件不入库目录**：分片落 `DataDir/uploads-tmp/`（具名常量 TempDirName）——未过四道校验的半成品绝不进媒体库；complete 时先预置成库根内 `.qm-upload-*.tmp` 同卷临时名（跨卷回退全量拷贝），锁内 rename 原子落位，与直传 #9 关键段同构（重活在库锁外，持锁时长与文件大小无关）。
5. **过期与清理**：无追加/终结活动 ≥24h（uploadsess.SessionTTL）的会话连同临时文件回收，另有孤儿 .part 清理（进程崩溃遗留，按 mtime 同 TTL）；清扫不 bump 修订号（未产生资产）。服务端优雅关停时尽力清空在途会话（CloseUploadSessions）。会话只在内存——服务端重启即全部失效，客户端重建会话重来（续传面向分钟级中断，不做会话持久化）。
6. **刻意不做**（记档）：并行分片乱序上传（单会话串行追加，客户端单发即可，2GB 内并发收益不抵复杂度）；校验和去重/Checksum 扩展（校验失败重传一片即可，秒级）；会话持久化与重启续传。
7. **目标目录 dir（初版刻意不做，同日补齐）**：`CreateUploadRequest` 增可选 `dir`，与直传 `POST /assets/upload` 的 dir 参数**逐字同语义**（库内相对路径、空/缺省 = 库根），create 时经与直传同一入口（resolveUploadDir）校验规范化后存入会话，complete 按其落位子目录（冲突解析/穿越兜底与直传同构）。初版记档的"协议无 dir、恒落库根"当时是有意的裁剪（COS 库子目录上传继续走直传通道），同日撤销补齐——原因：Web 拖拽目录递归上传（相对路径映射库内子目录）与 Android 带目录目标上传都是真实主链路，无 dir 会迫使子目录大文件整通道放弃续传（Android 被迫"有 dir 一律直传"），静默放错目录比不续传更糟、不续传又丢续传收益，唯有协议补齐两头兼顾。

## 状态（Status）

Accepted（2026-10-01）

## 后果（Consequences）

- **积极**：弱网大文件从中断即归零变为按片续传（服务端权威 offset，客户端零状态）；双通道（直传/分片）共用同一套校验与入库管线，事件、修订号、富化行为完全一致，对账无分叉。
- **代价与风险**：会话在内存，服务端重启放弃全部在途分片（接受——重建成本 = 重传整个文件，低于持久化机制的复杂度）；DataDir 与库根跨卷时 complete 多一次全量拷贝（NAS 部署两者通常同卷或 DataDir 在本地盘，拷贝可接受）；直传 `POST /assets/upload` 一字未动（协议与行为），小文件直传通道保留，双端按 size 阈值分流——双端已接入（Android 分流随 dir 入协议回归纯 size 判定；Web 批次传输层 XHR 直连不走生成 SDK——生成 client 请求选项无 abort 支持且全局 403 拦截器会误伤 UPLOAD_DISABLED 业务响应，选型记档 `web/src/lib/upload-chunked.ts`）。
- **联动文件**：`api/openapi.yaml`（3 路径模板 + UploadSession/CreateUploadRequest schema）、`server/internal/uploadsess/`（新包：会话注册表/分片文件/过期清扫）、`server/internal/httpapi/uploads.go`（5 handler + 清扫 daemon + 关停清理）、`server/internal/httpapi/upload.go`（抽共享 resolveUploadPolicy / ingestPlacedUpload / assembleUploadDetail / writeUploadValidationError，直传行为零变化）、`server/internal/httpapi/server.go`、`server/cmd/qimeng/main.go`、`server/internal/httpapi/uploads_test.go`（新）、`docs/GUIDE_API.md`、`docs/SECURITY.md`、`docs/CAPABILITY_MAP.md`、`docs/HANDOVER.md`、`docs/CHANGELOG.md`（第四百一十七笔）、`docs/adr/INDEX.md`。
