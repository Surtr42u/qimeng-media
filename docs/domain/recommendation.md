# 推荐与排行

> 本专题是领域规则正文；[领域目录](../DOMAIN_RULES.md)保留原 §编号。公式与常量保持原义，标记「逐字遵守」者未经用户明确要求不得改变。

## 1. 推荐算法（10 维自适应加权评分）

### 1.1 十维评分公式【逐字遵守】

| 维度 | 设计权重 | 计算方式 |
|---|---|---|
| tagRelevance 标签相关性 | 0.22 | 每个标签在所有已浏览文件中出现频次，归一化后取该文件标签的平均相关性；标签相关性数据为空时默认 0.2（同 tagCollection 空默认 0.15 的防饿死设计，2026-09-07 补记） |
| tagCollection 标签合集 | 0.15 | 文件标签集与用户 Top-20 偏好标签集的 Jaccard 相似度（\|交集\|/\|并集\|）；为空时默认 0.15 |
| engagement 互动热度 | 0.10 | (viewCount + playCount) / 全库最大值，归一化 0~1 |
| recency 浏览时效 | 0.15 | 距上次浏览天数衰减：<1天=1.0，<3天=0.8，<7天=0.5，<30天=0.2，更久=0；从未浏览=0.3 |
| likeScore 点赞 | 0.05 | likeCount / 全库最大点赞数，归一化 0~1 |
| discovery 发现 | 0.20 | 1 − min(viewCount/5, 1)，浏览越少分越高 |
| freshness 新鲜度 | 0.05 | 入库时间衰减：<1天=1.0，<3天=0.7，<7天=0.4，<30天=0.2 |
| browseDepth 浏览深度 | 0.03 | totalBrowseSeconds / 全库最大时长，归一化 0~1 |
| randomFactor 随机扰动 | 0~0.30 | 确定性随机：(assetKey hash xor seed) 取 16bit / 65535 × maxRandom，**同 seed 可复现，禁止纯随机** |
| dailyPenalty 每日去重 | 扣分额 0.8×n | 惩罚项不计入权重合计：今日已被展示 n 次则扣除 0.8×n，未展示为 0 |

固定权重合计 0.95（前 8 个加权维度）；随机项与每日展示扣分另计，共十维。最终分 = Σ(维度分×权重) + randomFactor − dailyPenalty（此处 dailyPenalty 为非负扣分额）。

### 1.2 自适应权重回收（数据空缺时自动重分配）

| 数据状态 | 回收 | 分配给 |
|---|---|---|
| 库内无任何标签 | tagRelevance(0.22)+tagCollection(0.15) | discovery ×50% + randomFactor ×50% |
| 无任何点赞 | likeScore(0.05) | freshness |
| 无浏览历史 | engagement(0.10) | discovery |

用户自定义权重作为**初始值**传入，回收逻辑仍然生效；数据完善后自动恢复设计权重。

### 1.3 用户可调权重与预设

8 个加权维度 + maxRandom 共 9 项用户可调（「推荐偏好」设置页），提供 4 个预设：

| 预设 | tagRel | tagColl | engage | recency | like | discov | fresh | depth | random |
|---|---|---|---|---|---|---|---|---|---|
| 均衡推荐（默认） | 0.22 | 0.15 | 0.10 | 0.15 | 0.05 | 0.20 | 0.05 | 0.03 | 0.30 |
| 高记忆流行 | 0.15 | 0.10 | 0.20 | 0.25 | 0.10 | 0.05 | 0.05 | 0.05 | 0.10 |
| 深度探索 | 0.30 | 0.20 | 0.05 | 0.05 | 0.02 | 0.30 | 0.02 | 0.05 | 0.40 |
| 新鲜优先 | 0.10 | 0.05 | 0.05 | 0.10 | 0.02 | 0.25 | 0.20 | 0.03 | 0.35 |

### 1.4 排序后处理（既有机制，必须保留）

1. **视频/图片自然混合**：评分排序后按剩余数量比例随机交错取视频/图片，避免连续分组；代价是牺牲部分排序精度换浏览多样性（有意为之）。
2. **同分桶随机打散**：seed>0（下拉刷新）时，按降序以每桶首项最高分为锚，落后不超过 0.05 的项进入同桶（含边界），桶内确定性随机打散。禁止按相邻分差不断延伸桶，以免连续小差值把高低分串成一个大桶；此为分桶边界修正，评分权重和 0.05 阈值不变（ADR-0045）。桶间分数顺序在后续类型混合前保留。
3. **每日展示计数**：服务端记录每个资产当日被推荐展示次数（当日零点重置），作为 dailyPenalty 输入；刷新不清零当日已展示计数。
4. **顺序快照（ADR-0046，2026-10-20）**：推荐流以（修订号、日界、seed、mediaType、cosOnly、权重快照）为键共享最多 60s 的完整 ID 顺序，offset/limit 不入键。首个请求装载完整候选并评分/混合，唯一排序/混合核心直接输出 ID（原 Item 接口保留完整字段和 Limit 行为），后续分页只切 ID、查询当前页元数据；不缓存协议响应或签名 URL。命中仍只对实际返回项累计展示计数；累计每日惩罚在快照失效后重算时生效，高频 open/play/dwell 不主动失效，结构变更即时作废。分页快照会因 TTL/容量淘汰/结构变更重建，客户端仍按 assetId 去重，不能承诺跨这些边界连续无重。
5. **容量与并发**：最多 32 个顺序、全缓存最多 100000 个资产 ID；清理过期条目后仍不足预算时整体淘汰，单个候选超预算不缓存但绝不截断候选。单飞内部二次查缓存，错误/panic 不缓存并释放等待者；失效前的迟到计算不得回填新一代缓存。页查询重新检查资产存在、启用库、媒体类型与 COS 归属，并发变更可不足一页。缓存只读、不形成第二份权威数据。
6. **预热与失效**：启动预热 App seed=1 与 Web seed=0 的常规流，分页大小不参与顺序键；预热不写展示计数。library.changed 覆盖扫描/watch/上传/整理/库开关等变更；导入完整成功或已有前段提交后发生失败/取消时，均推进持久修订号并广播，使 Web 的统计/排行/历史与推荐及时刷新。两种 seed 在同一修订号/日界/媒体/COS/偏好及评分时刻下，按需共用本轮一次完整输入装载、Item 转换与 seed 无关的标签/相关度/权重/归一化准备，但仍各自完整评分与保存独立顺序；不预先合并浮点维度求和，不改变随机项/桶洗牌/视频图片混合的调用次序；输入仅存活于本次预热，不形成常驻候选缓存，全命中时不装载。结构性失效时中止后续 seed 预热，迟到计算不能回填新一代；已共享计算的前台等待者仍取得正常结果，预热专用中止信号仅在同飞体外返回，不能变为前台请求的 500。计算所属代次固定，检查与登记之间再失效也不会把旧输入发布到新一代；正常请求与预热仍按原单飞键共享结果。预热不读取页摘要或写展示计数，首屏冷算仍需完整 ID 顺序，有短时分配与 CPU 代价，不以旧的限量算法基准代替本实现的端点性能。


顺序缓存仍限制为 32 流/100000 个 ID、60 秒 TTL。预算不足先删过期项，再按最近使用逐个淘汰足够的冷项；命中更新淘汰顺序，不延长创建时 TTL。超大单流完整冷算但不缓存，不截断候选，也不挤掉已有热点；Clear 仍清空并推进 generation，迟到计算不能回填。部分流被淘汰不保证分页跨失效边界永久稳定，客户端去重要求不变。

共享冷算使用 singleflight.DoChan，等待者取消只退出自己的等待，不取消其他前台或预热共享的计算；全部等待者取消后，已接纳计算仍完成并按原代际规则决定缓存。计算 context 属于 Cache 服务，关停停止准入、取消 SQL 并收齐计算后才关数据库；Clear 只阻止迟到发布，不把预热专用失效传给前台。纯排序为有限同步计算，不为取消改变算法或 RNG 调用。

不同键同时冷算最多 min(2, GOMAXPROCS)，按单用户 App/Web 两个独立流的用途收紧候选输入占用；单核为一份。超出者在请求栈上可取消地等候准入，不提前注册无界同飞体/后台 goroutine；同键等待者共享已接纳计算，不重复占预算。没有新增 HTTP 错误码、候选截断或 TTL 变化；服务关闭后拒绝新计算。合成闸门测试检查单核/双并发、不同键等待取消、取消与完成竞争及失效中的共享前台。

### 1.5 冷启动原则

无历史时优先混合不同类型/作者/出处；从未浏览文件 recency=0.3 不被完全忽略；新文件靠 freshness 获得基础曝光。

当前实现已有类型混合、标签/文件名信号和新鲜度；未实现作者/出处配额或连续同作者去重，不能把上述多样性目标当作已完成的硬约束。

### 1.6 输入装载策略与性能边界

`store.LoadRecommendationInputs` 负责只读输入装载，`recommend` 保持无 IO。默认未指定媒体、非 COS 的宽流保留原事件顺序聚合与全库标签两次读取；显式 mediaType/COS 流先观察总资产及合格候选数：候选不超过总数一半时，按候选资产索引读取事件、用参数化 JSON ID 集合读取标签；否则保留宽查询。空候选不读标签。比例是执行策略，不能当作评分参数；调整前须同时复测宽/窄集合与不同历史密度。

规模观察仅选择计划：实际输入查询重新判断启用库/媒体/COS 资格，即使 COUNT 后发生写入或观察值过时，也不得据此跳过查询或截断结果。两种计划保留完整候选、输入字段和 asset_id 顺序，候选标签顺序一致；原先额外读取的非候选标签不参与评分。资格谓词为 sqlc 静态 SQL，须由基线对照测试同时约束三处副本。排行继续使用原宽查询。决策见 ADR-0044。

评分权重、随机种子、后处理、60s TTL/单飞/预热及展示计数回写按 §1.1–1.5，不因读取计划改变。

### 1.7 算法评估与本轮调整

当前是单用户、无需训练的可解释规则推荐，适合少反馈的自托管媒体库。标签兴趣、熟悉内容、新内容、发现与每日去重都有独立信号；暂未有点击/长停留等离线对照结果证明改权重会改善体验。本轮保持评分公式、固定阈值、权重预设和缓存纪律，修正同分桶链式延伸，并减少标签重复计算/中间切片（ADR-0045）。评分后兼顾新鲜度与多样性的分层方式可参考 [Google 重排说明](https://developers.google.com/machine-learning/recommendation/dnn/re-ranking)；本项目适用性是代码审查判断，不是质量指标证明。

边界：兴趣与最大值归一化取当前启用库/媒体/COS 筛选后的完整合格候选，不是独立的全站用户画像；标签偏好只用已 open 文件的出现频次，没有时间衰减或负反馈。视频/图片混合仍可能改变跨类型分数顺序，按 §1.4 的既定多样性取舍执行。作者去重、偏好时间衰减等须有真实反馈评估后再改，不能因排序更随机就声称更懂用户。

纯算法基准（2026-10-20，Windows；2 万候选，固定时间/seed=42，返回 200 项，三次中位数）：图片流 36.36ms→24.42ms、混合流 36.52ms→26.28ms；累计堆分配分别 49.18MB→14.44MB/22.13MB。前后包含分桶修正及内存优化，输出顺序有意变化；不代表手机整页延迟或推荐质量提升。链式分差与精确边界、32 个 seed 可复现、固定评分维度和输入不被改写已回归。

```bash
go test ./internal/recommend -count=1
go test ./internal/recommend -run '^$' -bench '^BenchmarkRecommendLargeLibrary$' -benchtime=1s -count=3
```

#### 下标排序与限量混合（2026-10-20 后续优化）

纯算法在有限 Limit 下仍逐项评分、稳定降序排序并完成全部同分桶洗牌；中间行仅保存输入下标与分数。视频/图片两组也只保存下标，按完整组的剩余数量比例和原 RNG 顺序生成所需前缀，最终仅复制所需的 Item。当前顺序快照经同一算法的 ID 出口直接保存全部 ID，不再先装配完整 Item 数组；下列旧限量算法基准不是快照首屏耗时。不能先截候选再洗牌或按截断后的数量混合，否则同 seed 的顺序与翻页前缀会改变。输入保持只读，公式/权重/阈值、查询/缓存/展示计数不变，无新依赖。

优化前输出摘要锁定图片/视频/动图混合、seed=-1/0/1/42、同分稳定性；13 组完整顺序及每组 6 种 limit 的完整字段/前缀通过，另保留桶边界、固定维度和输入不被改写回归。

同一合成负载（2 万候选、seed=42、返回 200 项），Windows 三轮 `-benchtime=1s` 中位数：

| 场景 | 本轮前 | 本轮后 | 每次累计堆分配（前→后） |
|---|---:|---:|---:|
| 图片 | 25.34ms | 13.97ms | 14.44MB→6.96MB |
| 混合 | 27.61ms | 14.52ms | 22.13MB→7.13MB |

优化前 CPU profile 中 `runtime.memmove` 占采样约 19.6%，反射交换累计约 27.2%；分配主要来自完整 Item 的排序/打散/混合缓冲。缩小中间行并限制最终输出，减少搬运、GC 压力及小页返回时保留的整库缓冲；B/op 仍不是峰值 RSS。

### 短页与续页

推荐和排行响应恒带 `X-Qimeng-Next-Offset`：非负值是下一段原始顺序的 offset，`-1` 表示该轮顺序到底。资格复核可能移除本页全部条目，短页/空页仍可有下一段，不能据返回条数判到底。分页继续按原始顺序窗口推进，不为补齐当前页重扫全库或重复取尾部；展示计数仍只计实际返回项。旧服务端无该头时客户端才兼容页长判据。

Android 首页默认 COS 流与常规推荐共用服务端算法，传 `cosOnly=true`；下拉换 seed、本地分批揭示、触底换轮去重。应用非默认筛选/排序时使用 COS 资产游标列表，保留用户指定的条件与顺序；重置面板恢复 COS 推荐。客户端不打散或计算评分。

## 2. 排行榜

- 热度 = **窗口内** open+play 事件计数 + 窗口内点赞计数，降序（2026-09-18 用户拍板：原「viewCount+playCount+likeCount 全量累计」口径废止——累计值不随周期变化，切换 7天/30天 榜单不变；窗口化后周期榜随窗口滚动，Web/App 共用的 GET /rankings 单点生效）。窗口内 open+play 计数取自「资产×日」物化表 asset_daily_stats（day ≥ cutoffDay 的 view_count/play_count 求和；事件流仍是唯一真相源，物化表可随时重建，见 §5/§10）；窗口内点赞计数取自 likes 表的「资产×日」行（likes 主键 (asset_id, day)，day ≥ cutoffDay 计数——表自带日粒度，无需降级口径）。cutoffDay = 服务器当前时间减去周期窗口所得时刻的本地日历日（YYYY-MM-DD，按日取界：cutoff 当日全天活动计入窗口）。
- period=all：热度 = 全量累计（view_events 全量 open/play 计数 + likes 全量行数），与旧口径一致，零窗口聚合开销。
- 准入过滤与窗口聚合自洽（2026-09-18 起）：非 all 周期仅保留「窗口内热度 > 0」的资产（窗口内存在 open/play/点赞任一活动）；原「lastViewedAt ≥ now − 窗口」时间戳准入口径随窗口化废止——按日取界下与窗口计数边界日不一致，以窗口计数为准。
- 同分按文件修改时间（mtime）降序不变（2026-09-07 勘误保留：实现口径 = assets.mtime，行为由 TestRank_tieScore_newerModifiedAtFirst 锁定）。
- 周期：日/周/月/年/季（近 90 天）/总（period=quarter 为 2026-09-03 新增档位）。
- 排行不使用个性化推荐，纯热度。

### 排行执行策略与性能边界

`ranking.LoadPage` 编排只读取数、选页与摘要装载，HTTP 仅校验参数/签名摘要/序列化。小页通过纯函数 `RankTop` 选择完整排行的前 K 项，K 为 offset+limit+1（多选一项判断续页），并先按输入规模限上界以避免整数溢出；额外项不装载摘要、不计入返回页。K 小于输入规模时，标准库堆仅保留 K 个输入下标与预计算热度，堆顶为当前最差项；最后仅排序/复制这 K 项，再切页。热度、mtime 比较共用原全量排行口径，完全同分以输入下标保持稳定序。K 覆盖输入时沿用全量 Rank；offset 超过输入规模直接返回空页。窗口准入、常规/COS/启用库过滤、响应累计 viewCount/playCount 与不回写展示计数的语义不变。

小页排序辅助空间为 O(K)，时间上界 O(N log K + K log K)。整个请求仍要装载完整合格候选的热度键，不能先截候选再排序。总榜专用查询只投影 asset_id/mtime 与累计 open/play/点赞，不计算排行无关的 dwell/最近浏览/今日展示；周期榜仅聚合日物化统计及窗口点赞，不先装载全量原始事件。输入仍按 asset_id 排序以保持同分稳定序。选页后通过参数化 JSON ID 顺序仅读该页元数据、收藏、累计点赞及累计 open/play；周期排序使用窗口计数，卡片响应仍使用全量累计计数。返回页事件计数用既有 asset_id/kind 索引，无 schema/索引/协议变化。

两次读取不承诺跨查询事务快照；页摘要重新校验资产存在、启用库及非 COS，遇并发删除/停用/改 COS 可能不足一页，不泄漏已失去资格资产。不为只读请求引入取写锁的事务。旧完整推荐输入 + 分离窗口聚合 + 原全量 Rank 的逐字段/顺序对照覆盖各周期、页深、最大 offset、等时刻异时区、脏 mtime、仅点赞活动、无活动及隔离条件；并发变更与查询错误传播另有用例。
