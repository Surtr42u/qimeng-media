## 0. 总目标与执行原则

本任务书整合原有 `AI_MAINTENANCE_TASKBOOK.md`、`AI_MAINTENANCE_P0.md`、ADR-0051～0055 以及新增的独立 AI 接入层架构。

原任务书中已经确认的用户需求继续有效，不得因为新架构设计而遗漏作者维护、混合媒体整理、备份、后台任务或手机同步。

### 核心目标

建立一套独立于绮梦影库三端客户端、可以单独维护和升级的 AI 工具平台。该平台对外提供统一的工具调用能力，对内通过现有 Go 业务 API 完成数据查询与受控写入。

要求：

1. 不同 AI 通过统一入口接入，不需要重复开发业务脚本。
2. AI 规则、工具定义和工作流程可独立更新。
3. 新增 AI 工具原则上不修改 Web、Windows、Android 客户端。
4. AI 不直接写入 SQLite、TXT 主表或绕过正式文件业务流程。
5. 软件内部只有一套权威业务规则。
6. 保留当前手机内嵌 Go 服务端与 PC 独立运行的能力。
7. 兼容未来 NAS、常驻 AI 执行器和影视扩展。
8. 优先利用已有能力，禁止无必要地重新实现或引入大型框架。

**禁止把本次架构统一误解为推倒整个项目重写。**

允许调整 AI 接入层内部实现，但现有 Go 业务核心必须先审计，只有明确证明其实现不合理或能力不足时才修改。

## 1. 目标架构

### 1.1 总体结构

**外部 AI**（Codex、其他工具型 AI、未来模型或本地模型）

↓

**独立 AI 接入平台**

- 统一工具调用契约
- 规则包及规则加载
- CLI 接口
- MCP 适配器
- 可选 HTTP AI API
- 工具注册与版本管理
- 操作计划与确认
- 权限与凭据隔离
- 执行结果核验
- 后台任务适配

↓

**现有 Go 业务 API（`/api/v1`）**

↓

**Go 业务核心**

↓

**SQLite、TXT、媒体文件及备份**

同时：**Web / Windows / Android → 现有 Go 业务 API**；客户端不强制经过 AI 平台。

### 1.2 两套接口必须独立

**A. AI 工具接口**：面向外部 AI，工具名称、参数结构、工作流程及版本可独立演进；支持 CLI、MCP，未来需要远程调用时再提供 HTTP；版本独立于主 API。

**B. 现有业务 API**：面向 Web、Windows、Android 和 AI 适配器，继续以 [api/openapi.yaml](../api/openapi.yaml) 为权威定义；不得为了调整 AI 工具名称或研究流程而频繁修改主协议。

**两层接口不是两套业务后端。** AI 接入层只做工具适配、计划编排、安全控制和结果核验；作者、媒体、文件、备份等业务规则必须复用 Go 领域服务。

### 1.3 部署要求

独立 AI 平台应能够在 PC/NAS 上独立启动、停止和更新。第一版不强制增加独立 HTTP 服务或监听端口，优先采用本机 CLI 与 MCP stdio。允许独立发布 Python 工具包或等价可维护产物；具体实现语言以现有代码复用、依赖数量、打包难度和测试成本为依据。远程 HTTP、容器化和多 Worker 部署属于后续可选扩展。

### 1.4 执行编排与按需上下文（2026-11-10）

AI 不需要先读源码/完整文档才知道做什么：任务入口是**任务卡 + 可执行 recipe**。

- `qai task <recipe>` 返回 2–4KB 任务卡：目标、输入、步骤、工具/原语、人工门禁、产物与执行命令；不加载完整规则包。
- `qai run <recipe>` 逐步执行；只读步骤先跑，遇到 gate 停下；人工核对后同一运行目录 `--yes` 通过下一个门禁（多门禁需重复确认）；每步产物落盘（JSON + sha256），模型只拿有界摘要。
- recipe 是数据（`tools/ai_maintenance/recipes/*.json`），只引用注册表工具/原语；新增编排不改 CLI/MCP。
- 原语唯一实现：`media_primitives`（抽帧/dHash/拼图/缓存）、`device_adb`（显式真机）、`client`（统一 HTTP）；禁止为单个任务再写临时脚本。
- 运行目标能力先核对（`pc` / `android-embedded` / `nas`）：缺 ffmpeg/adb/research 时给出环境变量提示，不跑到一半才失败。
- 未知作者链路：`author.discover` = 抽帧/Google Lens 识图 → Bing/平台搜索 → `author.query` 查重 → 未命中才 `author.create` → `author.profile.prepare/update`（candidate，人工确认）→ `asset.authors.apply` → 回读。档案字段/证据/头像规则仍以 `tools/AUTHOR_RESEARCH.md` 与 `rules.json fields` 为准。
- 这是“按需加载”而不是“全量读取”：默认禁止把 `context` 全量规则包（约 477KB）或全部工具 Schema 一次性塞进模型上下文；需要细节时再 `platform.tool.describe` / `platform.rules` / `platform.playbook`。

## 3. 首先进行全项目定向审计

在修改代码之前完成以下检查。

### 3.1 工具与脚本清点

检查至少以下目录与文件：`tools/ai_maintenance/`、`tools/AUTHOR_RESEARCH.md`、`tools/MEDIA_RESEARCH_IMPORT.md`、`tools/import_creator_profiles.py`、`tools/audit_library.py`、现有研究脚本、导入脚本、数据修复脚本、`server/internal/research/`、`server/internal/maintenance/`、`server/internal/deviceapply/`、`api/openapi.yaml`。

对每一个脚本或工具记录：当前用途及调用者；输入、输出与依赖；是否直接联网；是否调用正式业务 API；是否涉及真实文件或数据库；是否具有写入副作用；是否有自动化测试；是否与其他实现重复；建议保留、封装、合并、隔离或退役。

不要简单把所有旧脚本复制进新平台。

### 3.2 脚本分类

- **AI 通用工具**（媒体清点、作者查询、作者资料准备、关联计划、结果回读）→ 纳入统一工具层。
- **可选研究工具**（平台查询、反向识图及研究证据整理）→ 由具备相应能力的外部 AI 或受控执行器按需调用，不作为 Go 服务端必需功能。
- **管理员专用工具**（数据库完整性审计、迁移、备份恢复、开发环境诊断）→ 保持独立管理，不能因为整合工具而默认对 AI 开放。

### 3.3 审计产物

形成一份脚本清单和复用/退役映射表，见 [AI 接入平台 R0 审计](AI_PLATFORM_AUDIT.md)。特别检查：相同业务是否被多个脚本重复实现；CLI 与独立填充脚本能否复用请求客户端和校验代码；研究接口与旧研究脚本是否存在不必要的重叠；是否有需要删除的过时规则；是否有 Go 端点存在，但规则包仍错误标记为未实现；是否有规则只存在于文档、未被正式服务端验证。

**验收：形成有证据的最小变更计划，再开始重构。**

## 4. 第一阶段：建立独立 AI 工具核心

### 4.1 目标

将当前 `tools/ai_maintenance/` 升级为可以独立维护的统一工具包。逻辑模块建议为：Context / Rules、Tool Registry、API Client、Plans、Execution、Security、Adapters（CLI/MCP/未来 HTTP）、Reports。不要求照搬这些名称建立大量空目录；只有出现真实职责时才拆分模块，避免为了架构形式增加复杂度。

### 4.2 工具注册机制

每个工具都应声明：稳定工具 ID、工具版本、功能描述、输入 Schema、输出 Schema、所需底层 API 能力、权限类型、是否只读、是否可能产生副作用、是否需要确认、超时及资源预算、错误码及恢复建议、实现状态。工具必须能够被发现、列举和独立禁用。新增工具不能要求修改统一入口中的大量条件分支。不要在第一版开发允许任意上传 Python 文件并直接执行的通用插件系统；可执行工具必须由可信发布流程安装并进行输入校验。

### 4.3 独立运行与更新

实现独立启动方式、版本查询、能力查询和健康检查。规则包及工具配置应能随独立 AI 平台发行物更新。如果支持运行中重新加载规则，必须：先校验新规则 Schema、版本及完整性；校验成功后原子切换；正在执行的任务保持原规则快照；新规则不兼容时暂停相应任务并要求重新制定计划；不允许模型通过普通工具调用修改权限规则或执行代码。

### 4.4 长期扩展性与按需发现（2026-11-07 用户补充）

工具数量持续增加时，外部 AI 不必每次加载所有工具的完整 Schema、业务规则和脚本说明；本项属于平台扩展能力优化，不推翻现有工具注册表、规则包、CLI 与 MCP 结构，不提前开发未来功能。

1. 提供按作者、媒体、研究、备份、设备、后台维护、平台等领域分类的精简能力目录。
2. 支持按领域发现工具、按需获取单个工具的 Schema、规则说明与示例，避免把完整规则包一次性塞入模型上下文。
3. 工具执行器按需加载相应代码模块；外部 AI 通过稳定工具接口调用，不要求阅读 Python 源码。
4. 模块内可独立增加、修改、废弃工具，并记录工具版本、规则版本和依赖的 Go API 能力；废弃工具默认从精简目录隐藏并保留替代指引。
5. CLI 与 MCP 必须共享注册与执行逻辑，按需加载不产生两套行为；MCP 保留标准完整 `tools/list`，同时提供符合协议的精简分类发现入口。
6. 区分权限与能力发现：AI 能看见某工具不代表有权执行，权限必须在可信执行端强制检查（`QIMENG_AI_GRANTED_PERMISSIONS` 或规则配置），未授权返回稳定错误码。
7. 评估当前管理员 Bearer 的绕过风险：AI 工具层隐藏 token 不能阻止模型直接调用 Go API；正式开放 AI 写入前应实现受限凭据或受限服务端权限，本轮只在文档与规则中记录风险与边界。
8. 增加大量工具注册、模块缺失、版本不兼容、规则变更、并发调用及禁用工具的自动化测试。
9. 保留现有 `/api/v1` 与三端调用方式，优先只调整 `tools/ai_maintenance/`，不为工具分类改写 Go 业务核心。

### 4.5 按需工作流模板与独立部署（2026-11-07 用户补充）

工具与规则按需发现之外，操作提示词、业务规范与工作流也要统一管理且不默认全量加载：

1. 工作流/操作模板（playbook）按领域登记在规则包，通过 `platform.playbook` 按需列目录或取单个；模板只是可选参考，AI 可自由组合基础工具，不强制按步骤执行。
2. 平台可独立启动、停止、配置与升级（CLI 单次进程、MCP stdio 由客户端拉起），不监听网络端口；HTTP 接入只保留扩展能力，本轮不实现独立网络服务。
3. AI 与 Go API 分别管理版本与兼容性；新增工具原则上不改三端；长任务继续复用 Go 维护任务账本。

**阶段验收：AI 平台能够独立运行只读工具，主 Go API 与三端应用无需修改。**

## 5. 第二阶段：规则包独立版本与兼容机制

现有规则包使用完整 OpenAPI 文件 SHA-256。该机制继续保留作为来源与构建追踪，但不得把任何主 API 字节变化都直接视为所有 AI 工具失效。

### 5.1 分离版本

至少区分：AI 平台版本、工具契约版本、规则包版本、主 Go API 版本、目标服务实例与业务数据修订、长期任务使用的计划版本。具体使用语义版本、能力集合或契约指纹，需在首轮审计中定稿。

### 5.2 兼容检查

AI 连接时先获取能力上下文。针对每个工具检查实际依赖的端点、方法、字段及业务能力。未通过检查的工具应明确标记 unavailable/incompatible，禁止让 AI 猜测旧参数继续执行。不要只根据「OpenAPI 中存在某个路径」就判定某工具完整可用。OpenAPI 解析与 Schema 校验采用可验证、锁定版本的方式，不继续扩大脆弱的字符串行解析实现。

### 5.3 主 API 修改规则

- 若现有 Go API 已具备能力，只改 AI 平台。
- 若只是规则变化，只改规则及相关测试。
- 若必须新增 Go 业务能力，先审查现有领域服务是否可复用。
- 需要修改 Go 协议时，继续 OpenAPI → SDK → 锁文件的正式流程。
- 破坏性变更需要兼容策略与旧客户端测试。

不允许通过复制数据库写入逻辑来规避主 API 的兼容要求。

### 5.4 Go 业务 API 完整性与 AI 客户端权限（2026-11-07 用户补充）

目标不是限制可信 AI，而是让 AI 能自由调用、组合、调度现有业务能力；Go 业务 API 应尽量完整、稳定、可组合，权限由 Go 真正执行。

1. 复核作者、媒体、组图、文件、备份、后台任务等现有接口，识别真正缺失的能力，不重复实现已有功能。
2. 完善 Go 层细粒度权限：支持专门的 AI 客户端凭据、授权范围（scope）与可撤销权限；允许用户主动授予可信 AI 较高权限，不强制所有日常写入逐项人工确认。
3. 区分低风险与高风险操作：常规作者资料补全、媒体关联与命名整理可在授权范围内自动执行；删除、不可逆覆盖、数据库恢复等支持单独授权策略。
4. 独立 AI API 保持独立升级（工具发现、按需规则、字段规范、脚本扩展、MCP/CLI 与任务编排），不在 AI 层复制 Go 领域业务逻辑。
5. 优先提供基础工具，允许 AI 自由组合；预制工作流是可选模板，不是唯一路径。
6. 权限校验由 Go 执行：AI API 不以长期持有全局管理员 Bearer 作为唯一授权方式；客户端凭据与普通用户会话区分，具备撤销与审计。
7. 长任务复用既有维护账本/Worker/暂停恢复/执行记录，避免第二套任务系统；NAS 场景下 Go 为稳定底座、AI 平台独立更新，手机不要求部署完整 AI 执行器。
8. 不为开放能力提供任意 SQL、无边界文件访问或任意服务器命令执行；特殊管理能力通过明确管理功能或受限执行环境。

当前 PR 优先收尾现有代码与测试：本项**先形成 API 缺口与权限模型方案**（[Go API 缺口与 AI 客户端权限模型](AI_PLATFORM_API_GAPS.md)、[ADR-0057](adr/0057-AI客户端凭据与细粒度权限模型.md)），按必要性分阶段实施，不立即重构全部接口、不阻塞现有交付。

## 6. 第三阶段：统一查询、计划与受控写入

### 6.1 查询工具

复用已有 CLI 查询功能并完善：`project.context`、`library.query`、`asset.query`、`author.query`、`author.profile.read`、`author.sources.read`、`maintenance.inventory`、`maintenance.status`。工具名称以最终独立契约为准。所有查询需要有界分页、超时、明确错误及安全输出。

### 6.2 写入工具

逐步实现：`author.profile.prepare`、`author.profile.update`、`author.cleanup.prepare`、`author.cleanup.apply`、`author.merge`、`asset.authors.prepare`、`asset.authors.apply`、`media.organize.prepare`、`media.organize.apply`、`backup.export`。不要求一次性实现所有工具。优先完成作者维护链路，再扩展混合媒体整理。

### 6.3 统一执行流程

任何写入动作遵守：**查询现状 → 生成计划 → 检查前置版本 → 确认/匹配已有授权 → 正式 API 执行 → 回读 → 记录结果**。

计划必须包含：目标实例、目标库与对象、变更字段、预计影响数量、已有值与拟修改值、证据来源、当前版本及计划指纹、权限和确认要求、幂等键、可恢复步骤、执行后的预期结果。高风险操作不得省略影响预览。

### 6.4 作者专项要求

必须继承现有规则：普通作者与 COS 作者体系隔离；作者标识和别名按领域规则处理；不以同名直接判定为同一创作者；`empty/candidate/verified` 状态需要有效证据；人工修改、人工清空字段优先保护；保存档案先读取 revision，409 时重新核对；X 原文与中文译文分开保存；头像来源、离线正文及展示状态分开处理；作者删除只删除作者及关联，不删除媒体文件；作者合并必须复用已有原子合并端点；改名撞身份不得偷偷执行合并；改挂作者时保护 TXT 作品行和来源区一致性。批量清理候选不得根据单一的零关联数量直接删除。

### 6.5 独立脚本迁移

将已有 `import_creator_profiles.py` 的成熟输入校验、人工资料保护和写入流程复用到统一工具核心。保留旧脚本兼容入口一段过渡期，内部逐步转发统一实现。禁止出现两份长期独立维护的作者资料写入算法。

**阶段验收：能够在隔离环境中完成作者读取、计划、合法修改、冲突处理及回读；人工资料无意外覆盖。**

### 6.6 组图命名与作品编号正确性（2026-11-07 用户补充）

**核心原则：作品编号与组图内部页码必须分离；作品编号按作品递增，不按图片文件数量递增。**

示例：已有 `守望先锋 朱诺 1.png`～`守望先锋 朱诺 10.png`，新到一组四张确认属于同一作品（无论原始文件名是规范的 `… 1`～`… 4` 还是浏览器下载的乱码名），应命名为：

- `守望先锋 朱诺 11 (1).png`
- `守望先锋 朱诺 11 (2).png`
- `守望先锋 朱诺 11 (3).png`
- `守望先锋 朱诺 11 (4).png`

该组只占用作品编号 11，下一部独立作品从 12 开始。**禁止把同一组图片分配为作品 11、12、13、14。**

实施要求：

1. 必须先识别作品分组，再分配作品编号，最后生成组内页码；三步不得合并为按文件逐个编号。
2. 文件名不规范时，结合来源条目、下载批次、目录与图片内容识别组图，不依赖原始文件名规范；无法确认时输出候选分组与预览等待确认，不得擅自拆成多个作品或错误合并。
3. 作品编号与组内序号分别维护；补图、改名、移动或重新排序不得无故改变整组作品编号（补图只追加页序号；缺页保留现状，不在未确认时重排整组）。
4. 兼容现有命名序号规则，支持单一作品与多张组图混合入库；组内页码格式为 `(1)`～`(n)`，作品编号沿用既有分隔与位宽规则。
5. 批量导入或并发操作必须防止作品编号冲突、跳号与重复分配：执行前重新读取目标库现状并校验计划前置指纹，写入后回读核对实际文件名；服务端自动改名（同名冲突）不得被当作成功，必须作为冲突终止并重规划。
6. 复核现有 Go 命名解析与作品数据结构，优先扩展现有纯函数与命名约定；只有确实无法保障上述约束时才提出最小必要 API 或数据模型修改（不得为此另建一套独立命名系统）。
7. 最终写入与命名执行环节必须强制校验，而不是只在提示词或工具描述里要求 AI 注意；测试覆盖乱码文件名、规范连续文件名、图组与单图混合、乱序、缺页、补图与并发命名。

## 7. 第四阶段：CLI、MCP 与未来 HTTP API

### 7.1 统一实现

CLI、MCP 和可选 HTTP API 必须使用同一套工具注册、校验和执行逻辑。不能出现 CLI 一套作者规则、MCP 又写一套、HTTP 再维护第三套。

### 7.2 CLI

作为最基础、最容易调试的工具入口。提供机器可读 JSON 输出、明确退出码、版本及能力查询；可直接用于本机 AI 和自动化执行器。

### 7.3 MCP

在工具核心稳定后实现 stdio MCP 适配器。要求：正确发现工具；输入输出 Schema 与 CLI 一致；工具调用有明确超时、取消和错误；不直接暴露管理员 Token；禁止注册任意 shell 或任意 Python 执行工具；至少使用两种不同 AI 客户端进行接入测试。

### 7.4 可选 HTTP AI API

只有实际存在远程 AI 客户端、NAS 执行器或其他网络调用需求时才实现。如需实现，应拥有独立契约和版本，不必加入现有三端共享 OpenAPI。不得为了独立接口强制开放公网端口。本机优先 stdio，远程优先可信网络及受控身份认证。

**阶段验收：两个不同 AI 客户端能够使用同一套规则与工具完成相同的合成任务，不需重新开发脚本。**

## 8. 第五阶段：统一后台任务与执行器

现有 `server/internal/maintenance`、migration 0023 和 `/api/v1/maintenance/jobs` 必须直接复用。

### 8.1 保留唯一任务账本

不得为独立 AI 平台新增第二套彼此不一致的任务状态数据库。任务仍使用现有持久账本记录：任务 ID、状态、输入指纹、工具/规则版本、授权、步骤与工件、费用及资源预算、失败及恢复信息。

### 8.2 Worker 架构

首先确定 Go 内部 Worker 与外部 AI 执行器的职责。推荐：Go 任务账本（持久状态、任务授权和任务结果）；独立 AI 执行器（研究、模型调用、工具编排及受控处理）；Go 业务服务（正式业务写入）；手机 Worker（领取并应用设备结果包）。

当前 Go 队列的 Claim/Heartbeat/Complete 仅是内部原语，外部执行器没有现成的领取接口。因此在实现独立 Worker 前，必须审查并定稿可信领取/续租/完成协议，避免外部工具直接写任务表。可以采用内部 Worker 桥接或受限 Worker 通道，但不能直接向普通客户端开放不受控的执行端点。

> **2026-11-08 更新（源码 + 本机定向测试，未安装）**：受控通道已实现——`POST /api/v1/maintenance/executor/claim`（无任务 204）与 `jobs/{id}/{heartbeat,steps,artifacts,complete}`，scope `maintenance.execute`；服务端每次领取生成 fencing `leaseToken`（30–1800 秒，默认 120），暂停/取消/终态/过期/重领后旧 token 一律 409 `LEASE_LOST`；claim 返回完整 `completedSteps`，>50 步任务恢复不再重复已完成副作用。真实外部执行器、多执行器并发与 NAS 未验收。

### 8.3 可靠性要求

- 有界并发、CPU/IO 和模型费用预算。
- 租约超时与进程重启恢复。
- 每一步独立记录状态。
- 操作完成事实必须能够回查。
- 重复提交不能造成重复副作用。
- 取消时保留已提交步骤记录。
- 人工授权等待态可恢复。
- 当前维护任务同一幂等键重复提交不比较新载荷指纹，应评估补充冲突保护，避免同键不同任务被误认为成功重放。

任何修改需审查主 API 兼容性。

**阶段验收：任务跨执行器重启能够恢复，不产生重复媒体、作者关联或浏览事件。**

## 9. 第六阶段：继承手机后台同步与两代备份

本节继承原任务书要求，不因为引入独立 AI 平台而取消。

### 9.1 当前基础

PC 服务端已有设备结果包 API、migration 0024 和 `deviceapply` 包；ADR-0057 P1 已加入 AI 客户端设备级 scope（device.apply + device_ids）。Android 后台 Worker 源码已按 §9.6 交付，但真机后台/SAF/内嵌服务可用性与自动应用尚未验收，设备配对短码/二维码仍未实现。2026-11-08 增：manifest 可选 `expectedState` 与服务端权威回读（migration 0026 `verification_json`，不参与幂等重放比较）；Android 领取/待办按 nextCursor 全量翻页（100/页、上限 2000）、本机模式自助设备令牌与只读最近任务卡已交付源码。设备配对/身份证明、临时包 GC 与真机后台仍未验收。

### 9.2 手机同步流程

固定为：PC/NAS 生成结果包 → 手机在充电与 Wi-Fi 条件满足时主动拉取 → 手机先导出本地完整备份 → 校验目标设备、协议、规则指纹与段摘要 → 按既有业务导入流程应用 → 回读核验 → 将结果回传 PC/NAS → 清理临时包，保留规定备份。

**不得跳过导入前备份。** 手机不新增入站监听端口，不依赖 USB，不强制用户保持 App 前台。

### 9.3 设备授权

`targetDeviceId` 作为不透明设备标签保留；P1 起由 AI 客户端 scope（device.apply）与 `ai_clients.device_ids` 在 Go 侧做设备级授权校验，专用设备令牌替代管理员 Bearer。真实跨设备自动应用前仍需真机验证重复领取、重复登记、不同设备误领、结果回传冒用和任务过期；短码/二维码配对未实现。审查重复领取、重复登记、不同设备误领、结果回传冒用和任务过期。保留手机系统对后台工作的限制，不承诺任何 Android 设备都能在精确指定时刻执行。

### 9.4 两代备份

按原需求实施：当前代、上次代两个独立文件夹，各有摘要。完整 v2 备份包含头像、作者档案和其他需要跨端迁移的资料。TXT 不能替代完整备份。旧三代布局迁移必须先备份、验证、保留回退路径；没有用户授权不得删除历史文件。

### 9.5 实际部署

目前手机内嵌 Go 服务端必须继续支持，不因 NAS 规划而提前移除。未来 NAS 接管长期媒体库后，再独立评估手机是否退役内嵌服务端。

### 9.6 Android 后台执行与 AI 权限适配（2026-11-07 用户补充）

当前没有 NAS，Android 内嵌 Go 后端长期保留；PC 端 AI 已能调用脚本/文件，Android 部分功能仍依赖 UI、后台与系统权限受限。本项在现有独立 AI API 架构上补齐：

1. 复用现有 Go API、设备结果包协议与维护任务账本，不建第二套业务系统。
2. 完善 Android 后台 Worker：在系统允许条件下主动领取、执行并回传设备结果包/维护任务，无需打开 UI。
3. 梳理 Android 文件权限、SAF 授权、后台运行限制与内嵌 Go 服务可用性；写入只使用用户已持久授权的目录。
4. AI 授权与手机执行权限衔接：设备标签 + 专用 AI 客户端令牌（scope device.apply + 绑定 device_ids），不绕过 Android 系统权限。
5. 能通过正式 API/后台任务完成的业务操作不再强制 UI；必须用户系统授权的操作保留 UI 入口。
6. PC 与 Android 使用统一业务规则，同时保留各自独立运行能力。

本轮只交付代码实现、权限适配与必要文档，不做完整测试、真机验收或实际安装；实现状态与待测项见 [Android 后台执行分析](android-background-execution.md) 与 [HANDOVER](HANDOVER.md)。

## 10. 外部搜索与联网研究的边界

### 10.1 默认执行方式

外部 AI 优先使用自身已获授权的搜索、浏览器、图片反向识别、视频帧分析、平台公开资料查询。研究结果记录证据、日期、出处与可信程度，再使用绮梦影库的受控业务工具进行写入。

### 10.2 现有 Go 研究网关

当前研究 provider/Lens 接口作为已有可选能力保留；`research.enabled` 保持默认关闭。本任务不增加：Fake-IP 地址段放行、为打通研究平台而放宽 SSRF 校验、非必要的研究专用代理、新的默认自动外网抓取服务。现有 Lens sidecar 未使用时不应自动运行。该规则仅针对研究网关，不应误停其他经独立授权的功能，例如现有头像获取或未来作者新作订阅。

### 10.3 历史脚本

保留有价值的研究策略、平台特征和证据判断规范。不要求把每个平台的搜索功能重新移植到 Go。可将成熟脚本登记为可选 AI 工具，但必须明确它需要的网络能力、权限与使用条件。当 AI 本身没有联网、浏览器或识图能力时，应产生待研究事项，而不是伪造核验成功。

### 10.4 自动追踪最新作品

属于未来独立功能，与「根据已有媒体寻找原作者」分开设计。当前不启动自动动态抓取开发，不将其作为统一 AI 接入平台的验收前提。

## 11. 安全与权限模型

### 11.1 基本要求

AI 模型不直接持有 Go 管理员 Token。AI 模型不直接获取任意 shell 执行权限或数据库写权限。可信本地工具执行器保管实际 API 凭据，校验模型请求后再操作。必须明确：当前 Go 主 API 仍以管理员 Bearer 权限为主；仅在 AI 工具层隐藏 Token，不能等同于服务端已实现最小权限。对于正式开放 AI 写入，应审查是否需要新增受限凭据或由可信执行器实施不可绕过的授权隔离。

### 11.2 操作权限

至少区分：只读查询、研究辅助、作者资料写入、媒体整理、高风险维护（作者删除/合并/批量改名）、管理员维护（备份恢复、迁移及管理员诊断）。权限必须绑定目标实例、目标库、授权目录和操作类型。工具注册表声明权限不等于真正完成权限隔离，必须有可信执行端或服务端强制校验。

### 11.3 安全不变量

- 业务写入只能调用正式 Go API。
- 不直接修改 SQLite、WAL 或 TXT 业务真相。
- 本地只读数据库审计仅限经过授权的可信维护工具。
- 文件操作限制在授权目录。
- 外部网页和模型输出视为不可信数据。
- 证据内容不能改变工具规则、权限或目标实例。
- 不导出管理员 Token、模型密钥、完整备份。
- 用户私人媒体样本对外提交前必须符合授权范围。
- 作者合并、删除、大规模改名先预览影响。
- 真实库 `8420` 禁止测试写入。
- Android 真机、模拟器与部署目标必须显式选择。

## 12. 扩展与长期维护要求

### 12.1 功能扩展

未来新增工具（示例：`media.duplicate.inspect`、`video.creator.identify`、`author.identity.review`、`anime.episodes.organize`、`series.metadata.prepare`）应优先通过新增工具模块实现。这些名称只是扩展示例，不代表当前必须全部开发。工具的新增、更新、禁用和废弃应有清晰版本机制。

### 12.2 不允许的扩展方式

- 每新增一个 AI 都复制一套脚本。
- 每新增一个工具都修改 Go 核心。
- 将任意第三方脚本默认授予管理员权限。
- 为不同 AI 单独维护不同业务规则。
- 同一业务数据出现第二套事实存储。
- 为尚不存在的需求提前建设复杂插件市场或分布式架构。

### 12.3 未来 NAS

独立 AI 平台与 Go 主服务应能在相同或不同可信主机运行。明确实例地址、凭据、工具版本、媒体根目录和任务归属。CPU、IO、内存、并发与模型费用预算分别管理。第一版继续使用现有 SQLite 与任务账本；只有实际规模、并发和性能证据证明不足时，才考虑更复杂的存储或任务基础设施。

### 12.4 未来影片、动漫和 AI 短剧

目前不属于本任务实现范围。但新工具接口不得把所有作品都假定为一个独立文件。后续可以扩展作品、季度、剧集与媒体文件的关系。这类业务数据结构变化应在未来 Go 领域设计中正式实施，不应通过 AI 工具层临时创建另一套作品数据库。

## 15. 每阶段的交付格式

执行者每完成一个阶段，必须交付：本阶段目标和实际修改范围；本阶段复用的旧代码和清理的重复实现；新增、修改、废弃的工具及接口清单；是否修改了主 OpenAPI、SDK、数据库迁移及其原因；兼容性说明与旧版本回退方式；单元测试、协议测试、集成测试、CI 状态；安全测试结果及已知风险；实际源码提交与 PR；构建、安装、运行、真实数据验证分别达到的状态；尚未完成的工作及下一阶段依赖。

## 17. 执行优先级与禁止事项

**优先级**：P0 现状审计与迁移计划；P1 独立工具核心、规则与版本机制；P2 受控写入、作者维护和 MCP 接入；P3 Worker、任务恢复及 PC/Web 管理；P4 Android 同步与两代备份；P5 NAS 与未来扩展。

**当前明确不做**：不重写整个 Go 后端；不重做已经存在的业务 API；不重新开发研究 provider 网关；不为 Fake-IP 添加安全例外；不启动自动作者新作抓取；不让 AI 自动生成或修改标签；不建设复杂通用插件市场；不移除现有手机内嵌 Go；不在本轮实现电影、动漫、AI 短剧；不将长期规划功能伪装成已完成。

## 18. 给执行 AI 的正式指令

请读取仓库 `AGENTS.md`、`AI_README_FIRST.md`、当前 OpenAPI、架构文档、原外部 AI 维护任务书和本任务书。首先核对最新 HEAD 与现有能力状态，明确哪些内容已经完成、哪些只是接口底座、哪些真正缺失。

本轮架构目标为：**建立独立于绮梦影库三端应用的 AI 接入与工具平台，通过现有 Go 业务 API 复用唯一业务核心。**

请从 R0 定向审计开始，先建立完整的脚本清单、接口依赖表和架构调整方案。R0 完成后，按照 R1～R8 顺序推进。各阶段保持可独立验收、可审查、可回滚；不得为了追求统一而推翻已经验证正确的业务逻辑。

优先实现独立规则加载、工具注册、统一 CLI、计划与受控写入，再增加 MCP；后台任务复用已有维护账本，跨设备同步复用已有设备结果包 API。

研究互联网资料优先由外部 AI 自带工具完成。Go 研究网关保持默认关闭，不能因兼容 Fake-IP 而放宽 SSRF 安全检查。

所有业务修改经过正式 API。保留用户原有作者资料、TXT、离线头像、v2 备份、浏览历史、标签和双端独立运行语义。

当前阶段以代码审计、独立工具架构和可验证的实施为重点，不启动无关 UI 重构、影视功能或自动作者新作抓取。

每阶段更新任务状态，交付真实提交、兼容性说明和验证证据。真实数据写入、破坏性清理和设备安装均遵守用户授权边界。

**最终验收目标：任意受支持的外部 AI 能够通过统一工具入口理解绮梦影库、使用自身研究能力、生成安全操作计划、执行已授权修改并验证结果；以后增加或修改普通 AI 工具，不再需要频繁修改整个 Go 主协议或三端应用。**
