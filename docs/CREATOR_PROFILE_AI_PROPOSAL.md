# 创作者档案与智能维护——需求与 UI 草案

> **文档状态：仅需求记录，未实现，未授权开发。** 2026-11-04 讨论整理。属于当前 `qimeng-media` 项目中为未来 App UI 试验及月底 Next 重构准备的**作者专题**；不是要求现在运行批量任务，也不包含其他重构事项。
>
> 视觉基准：[舒适型信息卡 UI 讨论稿](CONVERSATIONAL_COMFORT_UI_DRAFT.md)。当前项目已实现的身份、来源与关注语义，以 [作者领域规则](domain/authors.md) 和 [当前 UI 约束](GUIDE_UI.md) 为准。本文的新增字段、API、追踪功能均为**候选设计**，不能当成已存在功能。

## 1. 用户想达到的体验

用户主要收藏 X（Twitter）及其他平台个人创作者发布的 **3D R18 图片、3D 动画**，不是以传统 JAV 番号影片为主。用户目前手工维护作者名称和「搜索来源」；希望将已有作者管理升级为可逐步完善的个人创作者资料中心。

预期使用方式：

1. 用户继续沿用现有作者列表和手工录入习惯。
2. 可以只填现有作者名 / ID，让 AI **一次性搜索候选账号**；更推荐填 `@handle` 或 X 主页链接以降低歧义。作者可能只在 Pixiv、Newgrounds、个人站等出现，**不强制有 X**。
3. 经身份核对后，程序补全**头像、昵称、简介、主页、平台账号、别名、资料来源、最近核对时间**。
4. 可从作者页进入独立的「智能维护设置」，控制手动刷新和可选的新动态订阅。
5. 如果以后启用订阅，只展示作者新发布的**公开作品信息 / 预览 / 原帖链接 / 已读状态**；**用户自己决定是否寻找、获取与收藏授权可得的文件**。不做自动寻找付费作品免费副本、自动下载、自动替换本地原件。

期望是 **API 按需处理首批大量作者**；不是要求长期运行一个本地大模型，也不是让 AI 反复处理已确认的身份。

## 2. 两张喜欢的 UI 如何嵌入 App

### A. 作者档案主页（第一张，主页面）

保留原有作者管理和进入作者作品集合的路径，不另建一个与媒体库脱节的应用。主体遵循「人 → 作品 → 更新」的阅读层级：

```text
[返回] 作者名称                    [智能维护设置 ⚙]

  (头像) 作者名                         [关注]
         @handle · X / Pixiv / 官方主页
         简介（已核实且存在才展示）
         [资料状态：已核实 / 待完善]

  本地作品数量      最近收录（已有可信数据）

  [作品]  [动态（可选）]  [资料与来源]
   └ 现有作品 / 角色 / 类型筛选与媒体网格保持

  新动态摘要（已开启订阅且有真实数据时）
  · 新的视频预览 / 作品图片 / 原帖链接
  · 未读或已读；收藏情况未核实则不冒称「未收藏」
```

- 初期可先在现有 `AuthorCollectionScreen` 里加入**可折叠的轻量作者头卡**，而不强行引入多个 Tab；用户验收后再决定完整详情页结构。
- 头像缺失继续显示姓名首字，不取本地 R18 视频帧当作作者头像；长简介按需展开；新动态区关闭时不占空间。
- 作者列表现有的搜索、新建、全部/常规/COS、排序、关注、更多菜单、文件数全部保留。
- 原作者集合页日期分组、滚动、双指调整列数、文件筛选、详情导航及手势全部保留。
- Android 深色主题以 `MaterialTheme` / `QimengBrandColors` 为准，柔和中性卡面 + 低对比边框 + 清晰层级；不机械移植聊天 UI 的像素和色值。

### B. 作者智能维护设置（第二张，A 的二级页面）

这是**作者详情的设置子页/弹层**，而非另一个独立主项目。

- **平台身份**：输入或更换 X 用户名、X 主页链接，或其他平台的官方账号；显示已核实 / 待确认 / 冲突。
- **刷新作者资料**：手动重新查公开头像、简介、链接，预览差异后提交。
- **自动维护公开资料**：未来可选；用户手工锁定的字段优先，不得覆盖。
- **追踪公开新作品**：单作者单独开启/关闭，建议**默认关闭**；其他作者不随之启用。
- **身份冲突审核**：清楚显示候选账号及证据，用户选择合并、保留原账号或跳过。
- **更新与失败状态**：最近成功检查时间、来源不可访问、限流/权限不足、无新内容区分，不能将失败显示成「0 更新」。

### C. 作者管理中的批量补全入口

面向用户现有约 150 位作者的**一次性任务工作台**，不是每次启动都重新搜索：

- 基于本端已有作者名、别名及用户填写的链接，批量查找 X/其他平台候选；
- 展示「已明确匹配、待人工核对、未找到、抓取失败」的真实数量和每位作者的候选；
- 支持逐项或安全批量确认，失败可重试、任务可中断恢复；重复运行幂等；
- **先生成差异报告，再经用户确认写库**，避免误认作者而污染现有记录；
- 从未得到 API 凭据或模型未配置时，仍能纯手工维护作者。

## 3. API / AI 的职责边界

| 任务 | 更合适的责任方 | 约束 |
|---|---|---|
| 已确认账号的公开头像、昵称、简介、主页和账号变更 | 平台 API / 受支持的来源适配器 | 受费用、权限、限速、内容可见性限制 |
| 从作者名寻找可能的 X/Pixiv/官网身份 | AI + 搜索服务 | 输出候选和证据，不凭相似名自动合并 |
| 交叉验证官网、X、Pixiv 等关联账号 | 规则 + AI 辅助 | 优先官方主页交叉链接、明确身份凭据 |
| 定期获取已启用作者的公开帖子 ID 和作品链接 | 后台定时任务 | 已有数据去重；只按授权可访问的来源读 |
| 判断新帖是预告、原创、新作、旧作重发 | AI 可选分类 | 模糊时标记未知，用户自行判定 |
| 保存头像、作品关联和作者修改 | Go 后端 | 需事务/版本/来源保护，不让 UI 直接调平台或数据库 |
| 是否下载媒体及选取高画质版本 | 用户本人 | 不自动获取未授权资源 |

**不要强制用户部署本地 AI。** 一次性批量补全可由外部 API 完成；后续已确认账号的基本资料更新优先使用常规采集接口，仅歧义匹配/帖子分类等才调用 AI。API 凭据不能硬编码进 APK、日志或仓库；成本预算/限额应可见并可关闭。

X 账号的 `@handle` 可改名，因此身份关系尽量保存稳定的**平台用户 ID** 与历史 handle；但这与项目现有的作者 ID 是**不同标识**。X 官方接口与受支持的第三方检索方式都可能变化，不能保证全部 150 位或全部历史帖子都可找回。

## 4. 数据结构与现有功能兼容

**先保护已经投入使用的资料：**

- 现有普通作者 / COS 作者身份、别名、显示名、关注状态、资产关联及 TXT 重导保护不变。
- 现有「搜索来源 / sources」是**获取渠道与搜索词**，不直接等同 X 账号；不可为了补头像把它当成平台用户 ID。
- 作者档案的网络身份、头像来源、简介、更新时间、可信度、人工锁定字段等应设计为**独立附属元数据**，键关联内部作者身份。
- 涉及作者改名、身份迁移、删除、TXT 重建、COS 自动清理时，附属元数据应有明确迁移与清理策略，避免出现幽灵档案、头像串人、丢失人工确认。
- 后续如真要实施 schema/API 变更，必须按仓库增量迁移、OpenAPI 及备份规则同步，**此文不新增正式字段或迁移**。
- 头像缓存应允许离线显示，考虑图片缺失、链接过期和非安全外链；不将 R18 预览不经用户同意上传第三方 AI。
- 若未来有新作动态，原帖 ID / 平台 / 发布时间作去重键；帖子删除、权限变化时保留合适的历史状态，不伪造可访问内容。
- 动态提醒应支持 NSFW 预览隐藏、关闭通知，以及按需阅读；不把成人内容预览无条件放入系统通知。

## 5. PC、Android 内置 Go 与未来 NAS 的适配范围

现有项目已由 PC/Android **复用同一 Go 后端业务源码**，只是编译平台、运行路径和数据库实例不同。**本专题不提出重写两套后端或取消手机内置 Go。**

- **当前无 NAS**：手机本机模式和 PC 实例继续各自可用；作者资料补全应依赖统一的 Go API/数据模型，但**不假定两端 SQLite 自动同步**。
- AI 批量任务可以优先在 PC 上执行；手机不强制运行大型 AI。是否开放手机发起远程任务由后续连接、安全和成本设计决定。
- 新增作者档案数据应纳入未来数据迁移/备份的设计。真正的手机 ↔ PC 双向同步仍属单独需求，**本作者草案不许诺实现**。
- **未来有 NAS**：手机连接 NAS 时共用 NAS 的权威档案数据，届时可以不启动手机内置 Go；如果仍需保留单机模式，也应由用户选择，不影响作者页 UI。
- 不以「客户端代码和服务端代码同源」推断双端数据库身份一致，不能仅凭作者名称覆盖另一实例的作者记录。

## 6. 优先级与分批实施建议（非开工指令）

1. **P0 — UI / 领域模型方案与兼容验证**：两张页面的主从关系、身份字段、状态机、来源与备份影响；保留原作者列表和原文件集合。
2. **P1 — 资料展示及人工编辑**：头像、简介、平台账号、人工确认信息；原作者数据零破坏。
3. **P1 — 首次 AI/API 批量完善**：按名称/链接找候选、差异预览、批量确认、可重试，避免人工逐条复制头像和简介。
4. **P2 — 公开资料增量刷新**：可选更新、冲突保护、审计和配额控制。
5. **P3 — 新作动态订阅**：先手动刷新，再按作者选择是否自动检查；需要验证平台获取稳定性与费用。**可完全不做，不阻塞前四项。**
6. **明确排除**：自动寻找免费付费作品副本、绕过平台访问控制、自动下载/替换现有文件，以及本专题之外的完整多端同步或 Go 后端重构。

验收时应覆盖：完全无账号、仅作者名、同名创作者、改名、非 X 作者、头像失效、API 失败、额度耗尽、人工字段锁定、重复补全、已关注/未关注、手机单机未联网、长文字和小屏展示；所有统计/新作状态均基于真实返回值或明确示例数据。

## 7. 当前交付和后续使用方式

本文是**作者 UI 与功能的产品需求参考**，供这段时间在当前项目微调 UI，或月底 Next 重构时由 AI 再读现行代码、判断实现范围。它不是实施命令，也不应自动触发 GitHub 代码变更、真实数据迁移、网络抓取任务、付费 API 调用或设备部署。

**最终偏好摘要**：**主页面 A（创作者档案） → 内嵌设置 B（智能维护）；AI/API 一次性批量补全；新作品追踪为可选，下载永远由用户确认；保留现有作者及来源数据与手机本机模式。**
