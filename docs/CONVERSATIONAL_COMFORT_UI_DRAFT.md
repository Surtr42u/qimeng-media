## 1. 用户希望保存的设计意图

用户喜欢的不是某张卡片的单个颜色，而是这类界面整体给人的感觉：

- **安静、舒适、易读**：深色中性底、轻微层级，没有大片抢眼渐变和多余装饰。
- **卡片有呼吸感**：内容分组清楚，适当留白；信息丰富，但不拥挤、也不堆很多空壳。
- **一眼看出重点**：先看标题和最重要的状态，再看次级说明；图标用来辅助识别，不能压过文字。
- **信息是逐层展开的**：首先展示摘要，只在需要时展开详情、错误、技术数据、链接或管理操作。
- **真实可信的状态**：数据缺失、等待、失败、待确认和已完成明确区分；不把模拟的「新动态」误当成真实同步。
- **可以持续局部微调**：不要求一次性统一全 App；每次以小范围截图和实际使用反馈调整。

这组风格可以称为「**舒适型信息卡 / Calm Cards**」，只是内部讨论用标签，**不要求产品更名、引入 UI 框架或更新现有设计系统名称**。

## 2. 整体视觉语言：如何复现此前对话里的“舒服”

### 2.1 排版节奏

1. 页面级：标题明确、内容按任务分组；少用纯装饰型大标题。
2. 卡片级：**标题 → 可选一句解释 → 主要内容 → 可选分隔 → 次级动作**。
3. 列表级：**身份（头像/图标）→ 名称/摘要 → 关键操作**；第二行放次要信息；不要把一行塞进多个同权重按钮。
4. 功能级：让「现在发生了什么」「我能做什么」比纯技术参数更醒目。
5. 长内容靠自然换行与独立滚动容器解决，不用过度缩小字号。

建议先用现有间距 token 建立 **4 / 8 / 12 / 16 / 24 dp** 的视觉节奏（不是要求新增一套并行 token）。顶部和卡片间使用大档，标签/图标与文字使用小档。不要机械照搬聊天卡的像素值。

### 2.2 色彩与材质

Android 应以现有 MaterialTheme / QimengBrandColors 为准，当前深色主题已有：
- 页面背景：\`QimengBrandColors.BgDark\`（当前 #1A1A1A）。
- 标准卡面：\`QimengBrandColors.SurfaceDark\`（当前 #242424）。
- 柔和输入/内部信息块：\`QimengBrandColors.SurfaceSoftDark\`（当前 #2E2E2E）。
- 主次文字：\`TextPrimaryDark\`、\`TextSecondaryDark\`。
- 描边/分隔：\`DividerDark\` 或对应 MaterialTheme 语义颜色。

采用**少量明度差 + 细描边**来形成层次，而不是大量玻璃模糊、厚投影或高饱和卡片。默认状态标签维持低对比中性色；只有真正重要、少数的更新或失败状态允许清晰强调（例如少量蓝色「NEW」），**不要每行都上彩色标记**。

Web 保留自己的 [Aurora Glass](../web/README.md#设计语言adr-0031绮梦流光--aurora-glass2026-10-02-起) token 和视觉契约：**迁移的是层级、卡片布局和阅读节奏，不是把 Web 玻璃强套在 Android，也不是把 Android 灰色强套 Web**。

### 2.3 形状与组件

- 外层大信息卡：柔和圆角、细边界、与底色有可辨识的明度差。
- 内层状态块：通常比外层卡片更克制；**嵌套最多两级可见卡面**，避免「卡套卡套卡」。
- 头像：圆形；有真实授权头像时使用，缺失回退到姓名首字，不要自动拿视频封面冒充作者头像。
- 胶囊 / 标签：用作筛选或状态，颜色、密度保持一致；非操作状态不伪装成按钮。
- 分隔线：只在语义分组变化时使用，不要在每个小元素间画线。
- 图标：简单线性、同一笔画密度；仅帮助辨识模块，不额外创造无含义图标。
- 点击区域要有实际可操作的触控大小、焦点与读屏语义；视觉上较小的胶囊不等于可触控面积必须很小。

### 2.4 文案与信息密度

- 第一行优先展示「作者姓名」「新作品动态」「当前任务状态」，尽量短。
- 第二行说明「X · Pixiv · 主页」「本地 N 个文件」「已公开 / 待确认」等，颜色降低一档。
- 说明性文字可以有，但避免把长段功能说明当成页面主要视觉。
- 内容为空时，明确「暂未录入作者主页」「尚未检查公开动态」，**绝不填充伪数据**。
- 不强制添加「AI」标识；只在确实由 AI 推断的字段上标注「待核实」「推测来源」等。

## 3. 从本次对话提取的四种可复用信息卡模式

这次用户喜欢的**不只「创作者中心」卡片**，而是此前多组示意卡共有的表达方式：

| 对话中的示意 | 想保留的风格 / 用途 | 未来可能放入 App 的地方 |
|---|---|---|
| 创作者中心：头像、平台行、状态胶囊、新作列表、底部提醒 | **人物身份先行，动态次之**；新旧状态区分；一张主卡容纳完整概要 | 作者集合页顶部「作者资料摘要」或作者管理扩展入口 |
| 后台任务：扫描进度、缩略图、上传状态小卡 | **状态先行，辅助详情收起**；进度与错误清楚 | 维护、上传或后台任务页；当前仅视觉参考，不表示已有统一任务接口 |
| 流程示意：输入 → 分析 → 候选 → 确认 | **简单步骤 + 清晰间隔**；避免技术词淹没用户 | 首次连接、媒体整理、导入确认的说明向导（有需求才考虑） |
| 四天计划与新旧 UI 对照卡 | **分段、对比、分组**；标题醒目、次要说明低调 | 设置/管理工作区、对照/验收工具；不照搬实际日期和开发计划 |

**共同原则**：一个区域回答一个主要问题。操作应当可预期，内容适度合并，边界轻，重点清晰，不能因为“看起来漂亮”增加交互层数。

## 4. 作者相关页面：与用户现有 App 截图对照

### 4.1 现有作者管理列表（用户提供截图）

可见当前 UI 已有：返回顶栏、作者总数、搜索胶囊、新建作者、全部/常规/COS、排序、列表头像首字母、名称、文件数量、关注和更多操作。**这些成熟交互都应保留**。

适合以后尝试的仅是展示层：
- 有真实头像时替换首字母占位，没有则不变。
- 用户已录入主页时，可在副行或进入详情后展示来源平台的简短提示；现有「搜索来源词」本身**不是**可确认的平台账号。
- 若后续真的实现新动态查询，列表可按需显示很轻的「有更新」提示；没有数据时不显示。
- 关注、排序、筛选与更多操作保持当前触发位置和实际语义，不能让头像美化导致列表明显拥挤。

### 4.2 现有作者集合页（用户提供截图）

现状：标题为作者名、文件计数、作品/角色/类型胶囊、按日期分组的媒体网格；这些已有筛选、滚动、返回和手势行为应当保留。

适合探索的方向：**在原集合页中，先放轻量作者概要，再继续显示原有作品区**，不把已有作品浏览改造成复杂的信息门户。

信息结构草案（非真实界面、非实现要求）：

\`\`\`text
[ ← ]  作者名称

[ 圆形头像 ] 作者名称
             可核实的平台账号 / 别名
             简短简介（没有就不显示）
  [已关注] [主页链接] [资料待完善]

[ 本地作品 N ]  [最近收录 ]             ← 仅用已有可信数据

作品   动态   资料与来源              ← 仅为未来讨论的切换方案
----------------------------------
作品：继续当前作品/角色/类型筛选和日期分组网格
动态：公开新作条目、预览、发布时间、原始链接、待收藏
资料：作者别名、主页账号、头像出处、手动搜索来源
\`\`\`

**不应在首次尝试时贸然增设三个 Tab。** 可以先仅把头像、平台链接和一小段简介加在当前标题/计数之间；后续如动态内容足够丰富，再与用户讨论独立 Tab、折叠段或独立页面哪个更舒服。新内容并非已经写入媒体库；不能仅以标题相同就自动标记「已收藏」。

### 4.3 创作者概览卡（用户喜欢的对话示意）

主卡的阅读顺序推荐：

1. **身份**：头像、作者名、精简的平台标签/主页入口。
2. **状态**：已关注 / 未关注、资料待核对；仅真实完成同步时显示「最近已更新」。
3. **动态**：最多展示少量最新公开项目；每条为「图标或可用缩略图 + 标题 + 时间/说明 + 必要的新动态标记」。
4. **底部一句提示**：例如「发现新作品后可查看原帖，是否收藏由你决定」，不要重复做大按钮。

若无动态功能：整个动态区不出现或显示明确的功能状态，不生成虚假的「新 3D 动画」「新渲染图集」。

## 5. 数据语义边界（设计时必须知道，但此文不改领域规则）

本仓的 [作者领域规则](domain/authors.md) 明确：「来源」主要是**获取渠道/搜索来源词**，不是作品原始出处或已核实的作者账号。未来如果做作者头像和在线档案，必须**单独设计作者平台身份与外部来源记录**，不能直接把现有 \`sources\` 词数组当作 X/Pixiv 用户资料，不能由名称相似就自动合并作者。

新字段/能力可能包括（**仅概念草案，非现有 API**）：头像来源、作者主页、账号别名、资料最后核验时间、最近可见公开动态、已读标记。应区分人工录入、公开来源提取、AI 推断。自动更新不得覆盖人工校正的信息。

成人创作者内容可能受平台访问权限与隐私限制：不承诺持续获得 X 的完整动态、不预设有免费合法高清版本、不上传本地媒体关键帧到第三方，除非用户明确同意相关功能与数据处理方式。

## 6. 以后在 Compose 中如何落地（仅实施指南，不改任何代码）

当前源代码参照：
- 作者列表：\`android/feature/author/src/main/java/media/qimeng/app/feature/author/AuthorScreen.kt\`
- 作者集合：\`android/feature/author/src/main/java/media/qimeng/app/feature/author/AuthorCollectionScreen.kt\`
- 列表状态：\`AuthorViewModel.kt\`；集合状态：\`AuthorCollectionViewModel.kt\`
- 设计基础：\`android/core/ui/src/main/java/media/qimeng/app/core/ui/theme/{Color,Dimens,Theme}.kt\`

实现建议：
1. **第一轮只改展示**：在隔离预览/示例数据中绘制 \`CreatorOverviewCard\`、\`CreatorActivityRow\` 等候选无状态 Composable；名字仅建议，不意味着文件已存在。不要直接修改已安装版本。
2. **从已有 token 取材**：优先 \`MaterialTheme.colorScheme\`、\`QimengDimens\` 和当前卡片组件，避免新开平行主题。
3. **状态归属清楚**：数据读写与网络调用在 ViewModel/Repository；UI 只接不可变状态和动作回调。区分 loading、无资料、同步失败、近期已更新、未授权外部来源。
4. **保持原路由和网格**：优先在作者集合页原有内容上方加可折叠概览，原筛选和网格不要因卡片出现而丢失滚动、双指缩放和返回行为。
5. **单屏可读**：中小手机上优先两行排布，平台文字过长时换行，不让新增卡片挤掉文件内容。
6. **渐进交付**：先效果图/Compose Preview，再模拟数据交互，最后在单独授权的任务中讨论真实作者资料与动态接口。

不应仅因为视觉草案而修改 OpenAPI、数据库 schema、Go 服务端、真实作者记录或 UI 导航。

## 7. 每轮微调的验收清单

- [ ] 与用户提供的原版截图并排比较；保留原作者列表、关注、筛选、排序与文件网格。
- [ ] 深浅主题、窄屏、较大字体、横竖屏及状态栏安全区均无遮挡或溢出。
- [ ] 主次文字、图标、描边、胶囊与卡片的层级清晰；没有多余嵌套卡片。
- [ ] 长作者名、无头像、无简介、无账号、零作品、零动态、请求失败各有合理呈现。
- [ ] 新增图标/标签有真实语义；不可用的按钮不伪装为可操作。
- [ ] 关注和管理动作不受布局变化影响；媒体网格滚动与手势不退化。
- [ ] 用户认为「不舒服」时，明确改的是密度、间距、层级、样式还是交互，记录对照，不大范围盲改。
